kimageformats (UBSan build): parsing a malformed GIMP XCF image drives the XCF layer-loading routine to pull a stack of layer offsets straight out of the file and, for each one, seek the input stream to that offset before parsing the layer that is supposedly located there. With a corrupted file the offsets are bogus -- the run shows repeated warnings that the target seek position is wildly invalid (both huge positive values and negative ones), meaning the values read from the file bear no relation to the actual size of the input. The code does not check whether any of these seeks actually succeeded before going on to parse a "layer" at whatever position the stream was left sitting at once a seek request gets rejected, so per-layer parsing keeps running against a desynchronized stream instead of stopping. By the time control reaches the very end of the top-level XCF-decoding routine, where the image data accumulated so far is meant to be handed back to the caller by copying it into the caller-supplied destination image object, that destination object no longer looks like a validly constructed image in memory -- its runtime type information has been clobbered along the way. The copy performed at that final hand-off step is a virtual dispatch through the image type's base class, and because the object's type identity no longer matches anything the runtime recognizes, the sanitizer flags the call as undefined behavior rather than the parser producing a garbage-but-well-typed image or cleanly failing out.

fix_commit note: the commit pinned as the fix for this crash makes no change to any parser or application source file -- its only content is a single line added to a project housekeeping/ignore-list file, and it introduces nothing resembling a bounds check, a seek-result check, or any other validation anywhere in the affected read path. Diffing the full source tree between the vulnerable and "fixed" snapshots confirms this: the file containing the crashing routine is present in both, but every difference in it is cosmetic (license-header rewording, brace/spacing reformatting) with no logic change, and the gap between the two snapshots spans many unrelated commits and whole new format additions accumulated over a long stretch of time. This fix_commit is very likely a bisection artifact (the day-granularity build boundary happened to land on an unrelated repository-maintenance commit) rather than the actual patch for this bug, and should not be trusted as a description of what closes this crash.
