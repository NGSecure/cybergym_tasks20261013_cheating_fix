mupdf 在通过 `Do` 操作符渲染一个位图图像 XObject、且渲染范围只覆盖整张位图的一个矩形子区域时（例如图像被裁剪或只有一部分落在可见区域内），会在原始的、已解压出来的像素字节流之上再叠一层过滤流：这层过滤流按行工作，每行先跳过落在子区域左边界之外的若干字节，再把落在子区域内的字节原样转发给上层，如此循环直到把请求的所有行都处理完。

问题出在"跳过左边界之外的字节"这一步：这层过滤流认为只要向下游的原始像素流发起一次跳过请求，就能把这一行需要跳过的字节数一次性跳完；如果这次请求没能跳完全部数量（下游原始流因自身缓冲状态或数据即将耗尽，一次只肯让出一部分），过滤流没有对这种"没跳完"的情况做重试，而是直接把这一步解码当成"已经产出了一个字节"处理并返回，但它自己的读、写游标此时仍停留在函数一开始设成的"空"哨兵值上，从未真正指向任何有效缓冲区。

于是，负责判断"这条流里现在还有没有立刻可用数据"的通用查询逻辑，看到过滤流报告"产出了一个字节"，却发现游标仍是那对空哨兵值，就把"空指针往前退一格"得到的地址当成了这个字节的真实存放位置，据此汇报"这里有一字节数据可读，起始地址是这个"。再往上一层，负责把这批"可读数据"整块搬进目标像素缓冲区的通用拷贝逻辑，相信了这个汇报，直接对着那个由空指针回退一格算出来的、并不指向任何合法内存的地址发起读取。由于这张图片的每个颜色分量刚好占满一整字节、也没有启用颜色键遮罩，中间不需要再插入任何额外的中转过滤层，因此这次非法地址读取直接发生在这个最外层的通用拷贝逻辑本身，进程随即因为访问一个几乎全为一的非法地址而收到读段错误信号。工具把它报成一次由内存拷贝触发的段错误，而不是常见的"读到未初始化内存"提示，正是因为出问题的不是内容本身未初始化，而是被拷贝的源地址压根不是一个真实存在的内存位置。

fix_commit 判断：该 commit 唯一改动的一处逻辑，正是把"只尝试跳一次、跳不完就当作已产出一字节返回"的写法，改成了一个循环——只要还有字节没跳完就持续向下游原始流请求，并且一旦下游原始流某次明确报告"这次一个字节都没跳成"，就老实按"已到末尾"处理、不再假装产出了数据。这恰好堵死了上面这条"空哨兵游标被误当成真实地址"的路径：跳跃动作要么彻底完成才继续往下走，要么如实报告结束，不会再出现游标仍是空哨兵状态却谎称已产出数据的中间态。改动的位置与本次崩溃调用栈中负责"子区域跳字节"这一层完全对应，可信。

独立性说明：另有一条同样引用这个 commit 作为修复的崩溃报告（不同的 PoC 输入），触发路径与这里不同——那条报告里的图像每个颜色分量占不到一字节，解码时在这层"子区域跳字节"过滤流之上还需要再叠一层"位/样本拆包"过滤流，那条报告里的非法地址是被这层额外的拆包逻辑自己在其内部拷贝时使用并解引用的，而不是被这里描述的最外层通用拷贝逻辑直接使用。两条报告的直接崩溃函数、崩溃文件都不相同，是两个独立发现的触发路径，只是恰好都源自同一处"跳字节没跳完就冒充已产出数据"的根因缺陷，因此被同一个补丁一并修复，并不是同一次崩溃的重复提交。
