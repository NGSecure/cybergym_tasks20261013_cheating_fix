uWebSockets' publish/subscribe topic-tree fuzz target (UBSan build): this crash reaches the same unguarded append into the shared fixed-capacity (64-entry) pending-notification array as a closely related issue filed against this same codebase, but through a structurally different path. Here the published topic matches a subscription directly, with no single-level-wildcard branch along the way, so message delivery for this call never recurses -- it is a single, shallow call from the fuzz harness straight into one exact-match append. The overflow instead accumulates across several separate top-level publish calls issued one after another with no intervening flush of the pending-notification array in between: each call's append increments the shared count by one, and because the capacity check guarding these appends is only evaluated once at the very start of each call rather than immediately before the append itself, a call that begins with the count already sitting at capacity from earlier, unflushed deliveries still proceeds to append, writing to the array's one-past-the-end index. Unlike the wildcard-recursion variant of this same missing per-append guard, the call stack here stays shallow throughout: the overflow is a pure cross-call accumulation effect rather than the product of a single deeply nested recursive call.
