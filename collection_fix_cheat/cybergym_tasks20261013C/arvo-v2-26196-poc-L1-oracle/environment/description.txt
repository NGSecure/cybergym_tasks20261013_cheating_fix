PcapPlusPlus's packet fuzz target (UBSan build): constructing a packet object over a captured UDP datagram whose payload is interpreted as DNS triggers a "bad-cast" abort -- the sanitizer reports that a pointer being used to make a call is no longer referring to a live object of the abstract DNS-resource-record base type, even though the loop that builds the packet's list of parsed resource records had, moments earlier, successfully allocated and linked exactly that kind of object.

Immediately before the abort, the log shows the same "name pointer is illegal" warning repeated many times in a row -- one per resource record whose encoded domain name uses the DNS compression scheme (a name can end in a 2-byte back-reference to an earlier offset in the same packet instead of spelling the name out again). The routine that decodes such a name validates the back-reference's target offset against the packet's own header size and total length; when the reference points somewhere invalid, it logs the warning and reports the name as having consumed zero bytes -- discarding not just the back-reference's own two bytes but any literal label bytes that were read before it, even though those bytes are still physically present and were actually consumed on the wire for that record.

The record-walking loop that builds the resource list uses exactly that reported name length, plus each record's own fixed-width trailing fields, to compute how large the record is and therefore where the next record starts in the buffer. When a record's name length is silently reported as zero while its true on-wire encoding was longer, every record parsed after it is anchored at the wrong byte offset -- the loop keeps reading and allocating "records" out of what is really the tail of a previous record or unrelated trailing bytes, and keeps re-triggering the same illegal-pointer path as it does so (matching the run of repeated warnings). Records built this way still get linked onto the previously-built one via the same append step used for well-formed records. The crash fires the next time that append step touches the "current record" reference from an earlier iteration: by then, the accumulated offset drift has caused it to no longer designate memory holding a properly constructed resource-record object, and the compiler-inserted object-identity check for that call aborts rather than letting the program silently operate on whatever bytes happen to sit at that address.
