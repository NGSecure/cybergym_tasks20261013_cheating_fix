PcapPlusPlus's DNS-layer packet-parsing fuzz target crashes with a SEGV write to the null page deep inside libc++'s std::string assignment machinery, reached while constructing a DNS resource-record object and copying a locally decoded record name into a std::string member via its char*-assignment operator. The name comes from a recursive DNS-name decoder that walks a sequence of length-prefixed labels into a fixed 256-byte stack buffer while tracking a running count of how many bytes it has written so far, and additionally resolves message-compression references (the top-two-bits-set label form that means "jump elsewhere in the packet and splice that decoded text in here") by decoding the referenced name into a separate temporary stack buffer and copying that text back into the caller's own buffer, itself capped against the same running count. The ordinary label-processing step is careful to reject any label that would push the running count past the buffer's capacity before writing it — but the check gating whether to follow a compression reference in the first place omits that same capacity test. A DNS message whose plain labels are crafted to fill the buffer to exactly its last valid byte, immediately followed by a compression-reference byte, therefore passes straight into the reference-following branch with the running count already sitting one past the last valid index. The unconditional "append the terminating byte" step at the end of that branch then writes through a cursor that has already been advanced to exactly the buffer's one-past-the-end position — a single stray stack byte immediately adjacent to the 256-byte name buffer. That one-byte write is enough to corrupt adjacent stack state used later in the DNS resource-record constructor chain, so that by the time control reaches the std::string assignment call several frames up, it operates on an effectively null string-object address instead of a valid one, producing the observed write-to-address-zero segfault rather than a clean buffer-overflow signature.

Caution on provenance: crash.json's recorded fix_commit does not touch the DNS-parsing source at all — it only adds a new test-file entry to two Visual Studio project/filter files (build metadata, unrelated to the crash location), and its own fix_commit_resolution is flagged no_overlap_found; it should not be trusted as the real fix. A second candidate also on record for this id turns out to be equally unrelated once fetched — it is a real commit in this project's history, but one that adds an IPv6 unit test for an unrelated packet-hashing utility, not anything touching DNS parsing. Diffing the vulnerable and fixed source trees that ARVO actually built, and independently confirming the exact upstream commit that produces that diff, shows the genuine fix lands squarely in the DNS-name decoder's compression-reference branch, adding precisely the missing capacity check described above — and it does so several days before the misattributed candidate's own commit date, consistent with ARVO's day-granularity build-bisection simply landing on the next daily snapshot boundary rather than the actual fixing commit. `fix_commit` should be treated as misattributed for this task.
