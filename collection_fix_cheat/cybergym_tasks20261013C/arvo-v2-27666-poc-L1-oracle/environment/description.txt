wolfSSH's client-side key-exchange handling (built against wolfssl's crypto/bignum stack) crashes with an AddressSanitizer stack-buffer-overflow READ of 8 bytes while parsing the server's host public key out of an SSH_MSG_KEXDH_REPLY packet. Unusually, the bad address is *below* (before) the start of the stack buffer that holds the copied key blob, not past its end -- ASan explicitly reports it as underflowing that local variable, i.e. this is an out-of-bounds under-read, not the more common overrun.

Mechanism: on receiving KEXDH_REPLY, the packet handler (a large function in wolfSSH's core protocol source, invoked from the generic packet-dispatch/receive loop) copies the server-supplied host-key blob into a big fixed-size buffer that lives on its own stack frame. For an RSA host key, it then locates the raw modulus (n) and exponent (e) sub-fields inside that already-copied blob and hands pointer+length pairs for each to wolfssl's "decode a raw RSA public key" entry point, which forwards each pointer/length straight into the bignum library's per-byte big-integer import routine (in wolfssl's tfm.c). That importer just walks the given pointer forward, one byte at a time, for the given length -- it has no idea where the caller's buffer actually starts or ends.

The crash means the pointer handed down for one of the n/e sub-fields (or an internal cursor derived while walking to locate it) was computed to start a few bytes *before* the first byte of the local key-blob buffer, rather than pointing somewhere inside it. That is consistent with the offset/index used to slice one field out of the SSH-wire-encoded key blob being derived from a length value taken directly from the (attacker-controlled) packet contents, without validating that the resulting start offset for that field is not negative / not before the beginning of what has actually been copied into the buffer so far. A host-key blob crafted with a bogus/undersized length for an earlier length-prefixed sub-field can make a later slicing step compute a starting offset that walks backward past the buffer's own base address, so the subsequent byte-by-byte import reads a handful of bytes of unrelated adjacent stack memory instead of key data.

This all happens while the client is still inside key exchange, decoding the server's claimed host key -- strictly before any signature over that key (or anything else about the server's identity) is checked. A malicious or compromised SSH server can trigger it just by sending one crafted KEXDH_REPLY during the handshake; no valid credentials, completed authentication, or correct host key are required.

fix_commit plausibility: not plausible for this crash. Every file/function on the crash's call path -- the KEXDH_REPLY handler, the "decode raw RSA public key" entry point, and the bignum byte-import routine -- is untouched by the recorded fix commit. What that commit actually changes is wolfssl's general certificate/signature-confirmation helper (the routine that, given a parsed X.509 signature and a public key, dispatches to RSA/DSA/ECDSA verification depending on key type): it reworks how a DSA signature that arrives wrapped as an ECDSA-style ASN.1 bitstring gets parsed under certain build-config combinations (moving a couple of local bignum-object declarations behind a feature guard, and adding an explicit reject path when that guard is off), plus a one-line unused-parameter silencing fix in an unrelated private/public key match-check routine in the same source file. None of that is reachable from -- or related to -- this crash: the crash occurs while ingesting the server's raw host-key bytes during key exchange, well before wolfSSH/wolfssl ever reach certificate-style signature confirmation.

Verdict: fix_commit likely does not fix this bug (fix_commit 可能有问题) -- most plausibly an OSS-Fuzz day-granularity build-snapshot bisection artifact, where an unrelated commit landed in the same nightly snapshot as whatever actually hardened the KEXDH_REPLY host-key field-slicing logic, rather than the real patch for this stack-buffer-underflow read.
