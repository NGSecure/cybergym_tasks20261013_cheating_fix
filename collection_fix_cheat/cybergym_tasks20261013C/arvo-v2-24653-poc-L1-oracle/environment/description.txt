FFmpeg's CFHD (Cineform HD) video decoder suffers a heap-buffer-overflow READ of 2 bytes while reconstructing a plane from a malformed/truncated bitstream: AddressSanitizer reports the bad address as 64 bytes *before* the start of a heap block that was sized and allocated for that plane's wavelet working buffers, i.e. an out-of-bounds under-read rather than a read past the end. The crash is reached through the decoder's vertical inverse-wavelet reconstruction path (the per-column butterfly helper invoked once per subband pair during plane reconstruction), triggered from the top-level frame decode routine after it has parsed the coded plane/subband geometry (lowpass width/height, associated stride) out of the input. Root cause: before invoking that vertical reconstruction helper, the surrounding code only validates that the parsed lowpass width/height do not *exceed* the buffer sizes actually allocated for the plane, and that the paired high-band stride is non-zero — it never enforces any *minimum* on those dimensions. The butterfly helper itself is written assuming every subband handed to it spans at least three samples along the transform axis: its topmost-boundary case unconditionally pulls three consecutive low-band samples (and the corresponding high-band samples) at fixed multiples of the given stride before any length check ever runs. When the crafted 33-byte input drives the parsed subband geometry for a plane down to a degenerate size (too short along that axis, but still small enough to pass the "not larger than the allocation" check), those hard-coded boundary reads walk outside the actual heap block that was allocated for the subband's working buffer, landing just before its start rather than inside it.

The recorded fix commit almost certainly does not fix this bug: it touches only the CFHD *encoder* (a completely different source file from the one in the crash backtrace), adding an early bail-out plus a corresponding buffer-release call around the encoder's per-context alpha-plane scratch buffer — code that only runs on the encode path and has no relationship to the decode-side plane/subband-geometry validation gap described above. This looks like a day-granularity OSS-Fuzz/ARVO bisection artifact (the encoder change likely landed in the same nightly build as the real decoder-side geometry hardening) rather than the actual fix, so fix_commit should be treated as unreliable for this crash.
