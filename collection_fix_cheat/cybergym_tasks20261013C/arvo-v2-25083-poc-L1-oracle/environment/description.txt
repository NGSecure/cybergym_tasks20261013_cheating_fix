RDKit's V2000 molfile-to-mol streaming fuzz target (libFuzzer, MemorySanitizer build): a use-of-uninitialized-value fault fires much later than the actual bug, while checking whether a given atom index belongs to any of the molecule's substance groups -- a check invoked during hydrogen removal, well after the file has finished parsing. Root cause: the same dangling-bookmark bug seen in this family's other two members, but reached through a third, previously-unexercised SGroup property-line path. If a Marvin-style SMARTS property line earlier in the same V2000 property-line block swaps in a brand-new Atom object at an existing atom position, the molecule's in-place atom-replacement helper deletes the original Atom instance but never updates any bookmark still pointing at it, leaving the bookmark table holding a now-dangling raw pointer. If a later property line in that same block declares a substance-group attachment point ("SAP") by naming that same stale bookmark, the handler resolves the bookmark back to the freed Atom object and copies its stored index straight off the dangling pointer into the new attachment-point record -- silently carrying forward whatever bytes now occupy that freed slot instead of a genuine atom index. Under MemorySanitizer, freed memory is tracked as unwritten rather than immediately trapped, so nothing surfaces at that moment: the tainted value survives being copied again when the substance group itself is later duplicated into the molecule's permanent group list, and the sanitizer only reports a problem once that value is finally read and branched on -- specifically when a downstream consumer asks whether some atom index is covered by this group's recorded member atoms, parent atoms, or attachment points. So, as with this family's other two members, the crash requires two property lines to fire in the right relative order within one CTAB block: first one that replaces an atom carrying a live bookmark, then an attachment-point line that consumes that same bookmark afterward, by which point the object it named has already been destroyed. The distinguishing detail versus its two siblings is which SGroup property-line tag does the consuming, and that the eventual sanitizer report points at a much later, logically unrelated-looking call site (an atom-membership check reached from hydrogen removal) rather than at the bookmark resolution itself.
