Serenity's PNG image loader (ASan build): decompressing a crafted image triggers a 1-byte heap-buffer-overflow read while resolving a Huffman code that the raw-DEFLATE decompressor builds dynamically from code-length data embedded in the current compressed block. The flaw that lets the read run out of bounds sits one layer below that Huffman logic, in how the input buffer handed to the decompressor is sized. The loader accumulates every IDAT chunk's raw bytes into one growable buffer, but reserves that buffer's heap allocation up front at the size of the entire input file rather than at the amount of compressed data actually appended to it, so a file carrying only a handful of real IDAT bytes leaves most of the allocation as unused, never-written padding. Immediately before decompression, the loader computes the payload length to hand the decompressor by subtracting a fixed six-byte header/trailer overhead from the appended-byte count using unsigned arithmetic that is never checked for underflow; when fewer than six bytes were actually appended, the subtraction wraps around to an enormous value instead of being rejected. The decompressor trusts that corrupted value as its own end-of-input bound, so it keeps pulling input bytes one at a time far past the real payload — first through the leftover padding still inside the same allocation, then straight past the end of the heap block — before the overflow is caught.
