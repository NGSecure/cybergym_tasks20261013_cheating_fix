FFmpeg's DXTORY video decoder, when unpacking a vertically-flipped raw 4:2:0-subsampled frame whose height is odd, writes one whole luma (Y) row outside the decoded picture buffer (a heap-buffer-overflow WRITE, landing just before the buffer's start rather than past its end — the overflowing access is a single 2-byte packed pixel write, distinguishing it from the smaller single-byte chroma stores the same loop iteration also performs, which stay in bounds). Root cause: to realize the vertical flip without a separate copy pass, the decoder first points its luma write cursor at the frame's last row and negates the row stride, then derives a second cursor for "the next row" by adding that same (now negative) stride — so each pass through the main unpacking loop advances two row cursors together, walking backward through the buffer one row-pair at a time. That loop is driven by an unconditional step-by-two over the full frame height with no odd/even accounting: for an odd height, its final iteration still starts on the single remaining real row (the topmost one) and still writes through *both* cursors, so the second cursor — one more row-stride past the first, i.e. one row before row zero — writes outside the allocated buffer entirely. The upstream fix caps the paired main loop at the largest even row count not exceeding the frame height, and adds a separate trailing block, only entered when the height is odd, that unpacks the single leftover row using just the first (in-bounds) cursor — never advancing to the unsafe second one — while also filling in the correspondingly-shaped leftover column case and tightening the related input-size checks so a truncated packet can't reach the unpacking loop at all. The same commit separately corrects a rounding bug (floor vs. ceiling) in how this decoder's shared vertical-flip setup helper positions its chroma-plane cursors for odd heights; that is a real but functionally distinct off-by-one in the same file, not the mechanism behind this particular crash. The identified fix commit is credible for this crash: its patch touches exactly the source file and the specific decode routine the crash backtrace runs through, its own commit message explicitly describes fixing "subsampled formats with non-aligned size" in this same decoder, and the paired-loop bound it introduces is precisely the mechanism that explains the observed out-of-bounds write landing one row before the buffer's start.
