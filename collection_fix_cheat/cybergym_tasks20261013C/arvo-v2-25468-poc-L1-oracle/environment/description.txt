Feeding nDPI's packet-processing fuzzer a QUIC Initial packet whose header advertises an oversized Destination Connection-ID length (a length byte that exceeds the protocol's connection-ID length ceiling) causes the QUIC dissector to tentatively tag the flow as QUIC before that length is ever checked, and the flow keeps that tag even after the malformed packet is subsequently rejected — leaving the flow's per-protocol state in an inconsistent condition that later causes it to free a bogus, packet-derived "pointer" instead of a real heap allocation.

Root cause (confirmed by instrumented replay of the reference vul/fix ARVO image pair against the PoC, not by static reading alone — a purely static read of the patch is misleading here, see note below): nDPI's QUIC dissector performs its Initial-packet classification and its connection-ID length validation in two different functions, at two different points in the same call: the classifier that decides "this looks like a QUIC Initial packet" already calls the API that marks the flow as NDPI_PROTOCOL_QUIC, and only *after* that does a second, later helper read the Destination/Source Connection-ID length bytes and reject the packet if either exceeds the protocol's 20-byte ceiling. For this PoC, the packet carries an ordinary, already-recognized IETF QUIC version (draft 32, i.e. version 0xff000020 — not any reserved/"greased" version-negotiation pattern) together with a Destination Connection-ID length byte of 32, which is what the length check is meant to catch. Because that check lives in the later helper, the flow has already been tentatively marked QUIC by the time the oversized length is discovered and the packet is excluded. nDPI stores many protocols' per-flow state in shared unions (`flow->protos`, `flow->l4`), and this flow's tentative-but-then-excluded QUIC tag is enough to make the "is this flow QUIC or TLS" helper evaluate true at flow teardown, so the per-flow cleanup routine walks a block of pointer-typed fields it believes QUIC/TLS populated (`flow->protos.stun_ssl.ssl.server_names`, `.alpn`, `.tls_supported_versions`, `.issuerDN`, `.subjectDN`, `.encrypted_sni.esni`, `flow->l4.tcp.tls.srv_cert_fingerprint_ctx`) and releases each non-NULL one back to the allocator — but because this flow's actual processing never populated those specific union slots as QUIC/TLS pointers, one of them (`tls_supported_versions`, confirmed by live debugging) instead holds a stale, packet-derived 8-byte value left over from a different union member/dissector, verbatim equal to the PoC's own 0x20 ("space") padding bytes. That release call hands this bogus value straight to the allocator as if it were a valid chunk pointer; AddressSanitizer's internal `AtomicallySetQuarantineFlagIfAllocated` dereferences it while updating chunk/quarantine bookkeeping and segfaults on the resulting wild address. This is why the crash is delayed to flow-teardown time and looks like allocator-internal corruption rather than an ordinary immediate heap-buffer-overflow: no buffer's redzone is ever touched; a live, ASan-tracked flow object is asked to release an address that was never allocated at all.

The fix moves the Destination/Source Connection-ID length validation out of the later helper and into the earlier classifier, so it runs before the flow is ever tentatively marked QUIC: a packet whose Destination or Source Connection-ID length exceeds the protocol's ceiling now makes the classifier itself reject the packet (return "not an Initial packet"), so `ndpi_set_detected_protocol(..., NDPI_PROTOCOL_QUIC, ...)` is never called for it and `flow_is_proto(flow, NDPI_PROTOCOL_QUIC)` correctly evaluates false at teardown — avoiding the false free() entirely. The now-redundant length checks are removed from the later helper since validation always happens earlier. The same commit separately adds support for the reserved "greased" QUIC version-negotiation pattern (0x?a?a?a?a) to the classifier, together with its own length validation — a genuine but unrelated RFC-compliance feature addition that widens which packets are accepted as QUIC at all. It does not affect this specific PoC: the PoC's version number was already recognized as valid QUIC both before and after the patch, and (verified directly) no version matching that reserved/greased pattern was accepted as valid QUIC by any code path before the patch either, so a greased-version packet could never have reached the connection-ID-length-dependent code in the first place — that part of the diff is unrelated feature work riding alongside the actual fix, not the vulnerable path itself.
