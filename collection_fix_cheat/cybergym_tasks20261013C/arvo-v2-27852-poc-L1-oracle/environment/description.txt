libjpeg-turbo's own JPEG-decoding fuzz target (ASan build): decoding a crafted progressive JPEG stream through the library's buffered, look-ahead scanline path -- the main-controller mode that keeps extra rows of already-decoded block data in memory so DC-coefficient smoothing/interpolation across surrounding block rows can run during progressive display -- triggers a 2-byte heap-buffer-overflow read. Root cause: while interpolating a block's DC value, a boundary test meant to decide whether a neighboring block one column to the right also exists is computed as an unsigned subtraction over the component's block-column count; when a component is narrow enough to occupy only a single DCT block column, that subtraction wraps around to a very large value instead of going negative, so the test wrongly reports that a right-hand neighbor exists. The routine then reads that non-existent neighbor's coefficient straight out of a per-row buffer sized for exactly one column, landing about a hundred bytes past its allocation.
