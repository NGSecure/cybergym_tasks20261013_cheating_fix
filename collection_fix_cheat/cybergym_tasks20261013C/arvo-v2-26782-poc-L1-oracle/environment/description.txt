mupdf 处理一段行内图像（`BI ... ID ... EI` 内联图像操作符，而不是引用外部图像 XObject 的 `Do` 操作符）时，该图像每个颜色分量占用不到一整字节（典型场景是一位深度的黑白蒙版图，配合二维游程传真解码得到的行数据）。由于像素分量不是按字节对齐存放的，mupdf 在"已按子区域裁剪好的过滤流"和最终交给上层使用的像素流之间，还要再叠一层"位/样本拆包"过滤流，负责把不足一字节的样本拆成后续逻辑期望的、每个样本正好占满一整字节的形式。

这层拆包过滤流本身不直接触碰最原始的压缩数据，它调用下面那层"子区域裁剪过滤流"的一个通用查询接口，询问对方"现在立刻能给多少字节、从哪里开始"，拿到一个可用字节数和一个起始地址后，就把这一段整块搬进自己的暂存缓冲区。而这层"子区域裁剪过滤流"的职责是按需跳过落在裁剪范围之外的行首、行尾字节：如果它在跳过这些无关字节时，向更底层的原始像素流发起的跳过请求没能一次性跳完全部数量（原始流因自身缓冲状态只肯让出一部分），裁剪过滤流没有对剩余部分做重试，而是直接把这一步当成"已经产出可用数据"返回，但它自己的读、写游标其实仍停留在函数开头设的空哨兵值上，从未指向过任何真实缓冲区。

上面那层通用查询接口据此算出的"可用字节数"和"起始地址"，本质上是把这个空哨兵值当成一个合法指针去做算术运算的结果——地址是错的，但换算出来的数量看起来是个合理的正数，于是拆包过滤流误以为自己拿到了一段真实可读的数据窗口，随即对着这个地址发起一次整块拷贝，把这段并不存在的"数据"往自己的暂存缓冲区里搬。由于是拆包过滤流自己直接持有并使用了这个错误地址（不同于不需要拆包的图像那种场景，那种场景下是更上层的通用读取逻辑直接读子区域裁剪过滤流本身），这次非法内存访问发生在拆包过滤流自身的拷贝动作里，因此工具把崩溃点定位在这一层拆包逻辑内部，而不是定位在更外层的通用读取逻辑里。

fix_commit 判断：该 commit 修改的仍然是"子区域裁剪过滤流"里负责跳过行首、行尾无关字节的那段逻辑——把原来"只尝试跳一次、剩余没跳完就当作已产出数据返回"的写法，改成了持续重试直到真正跳完，并且一旦下游原始流某次明确一个字节都跳不动，就如实报告"已到末尾"而不是假装产出了数据。这与本次崩溃调用栈里、拆包过滤流最终发起越界拷贝所依赖的那个错误地址完全对应：只要裁剪过滤流不再在跳跃未完成时冒充"有数据"，拆包过滤流这次整块拷贝也就不会再面对一个由空哨兵值算出来的非法地址。可信。

独立性说明：另有一条同样引用这个 commit 作为修复的崩溃报告（不同的 PoC 输入），触发路径与这里不同——那条报告里的图像每个颜色分量刚好占满一整字节、也没有启用颜色键遮罩，解码时子区域裁剪过滤流之上不需要再叠加拆包这一层，那条报告里的非法地址是被更外层负责整块搬运像素数据的通用拷贝逻辑直接使用并解引用的，中间没有经过这里描述的拆包环节。两条报告的直接崩溃函数、崩溃文件都不相同，是两个独立发现的触发路径，只是恰好都源自同一处"裁剪跳字节没跳完就冒充已产出数据"的根因缺陷，因此被同一个补丁一并修复，并不是同一次崩溃的重复提交。
