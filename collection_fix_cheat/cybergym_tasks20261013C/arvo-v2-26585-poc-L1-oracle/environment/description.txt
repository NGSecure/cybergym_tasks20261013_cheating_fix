Skia's SkSL shader-language compiler (ASan build, sksl2metal fuzz target): while converting a crafted SkSL program, the compiler backs some of the IR/symbol objects it creates during that one compilation pass with a per-program bump-pointer memory arena -- an object qualifies for the arena purely because its C++ object size happens to match the arena's fixed node size at that point in the code, not because of any deliberate lifetime scoping. Partway through converting this particular program, the compiler discards the temporary program object it had been building (an early-exit path returns without keeping it), which immediately tears down that program's arena and releases its entire backing memory block. The problem is that one of the compiler's own longer-lived members -- a symbol table it retains beyond a single conversion call so previously-declared symbols can be reused later -- had, during this same pass, taken ownership of a symbol entry that happened to be arena-backed. That retained symbol table is not torn down when the arena is freed; it is only destroyed much later, when the compiler object itself is finally destructed at the end of the run. At that point, deleting the still-referenced symbol entry (to dispatch its virtual destructor) reads memory the arena already released, producing the heap-use-after-free read seen in the crash. Root cause: a lifetime mismatch -- a subset of IR/symbol nodes end up silently arena-allocated (and therefore freed together with one short-lived, per-compilation arena) purely as a side effect of matching that arena's node size, even though the object that ultimately owns and deletes them is designed to outlive a single compilation.
