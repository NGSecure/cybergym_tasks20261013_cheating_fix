Apache Arrow's Parquet-to-Arrow column reader crashes with a heap-buffer-overflow read while assembling a single row group's leaf column data from a fuzzed Parquet file. The reader's page-fetch loop parses the encoded header of the page it is about to hand back, and for pages that use the newer "version 2" data-page framing, the definition/repetition level payload attached to that page is always physically present at the very front of the page's byte range in raw, uncompressed form, ahead of whatever value data follows (which may itself be compressed with a real codec). Before running any codec, the reader first relocates that unmodified level payload into its own working buffer with a single raw byte copy, sized from two 32-bit fields taken straight out of the just-parsed page header — the repetition-level and definition-level byte counts, added together — with no bound imposed against how many bytes of page data the reader actually has in hand for that page. A crafted file whose header declares a combined levels length far larger than the number of page bytes physically read from the stream causes that very first raw copy to read straight past the end of the small heap allocation backing the current page's byte range. The overflow happens on the source side, before any codec is ever invoked, so it is reachable regardless of which compression codec is nominally selected for the column, and it fires unconditionally the moment a page claims to be large enough to need one. The eventual fix closes this by rejecting a page outright, before either the level copy or the subsequent value-decompression call executes, whenever either of the header's own compressed- or uncompressed-byte-count fields is smaller than the declared combined levels length — a bound that was previously altogether absent from this code path, leaving the level-copy step trusting attacker-controlled header arithmetic with no cross-check against the actual amount of data present.
