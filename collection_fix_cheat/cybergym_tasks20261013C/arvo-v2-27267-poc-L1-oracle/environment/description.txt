This MATLAB MAT-file (version 5) parser reports a use-of-uninitialized-value fault, but the uninitialized value is not read where it was produced -- it is only touched much later, deep inside cleanup code, which makes this a distinct bug from a simple "forgot to check this one read" case. When a variable header specifies that the variable is multi-dimensional, the reader loops over the header's dimension list one fixed-size word at a time, reading each dimension value through the same shared low-level byte-read helper used everywhere else in the parser and writing each one into the variable's persistent dimensions array as it goes. After the loop finishes, the caller performs a single post-hoc sanity check before accepting the result: it looks only at whether the loop transferred zero bytes in total, combined with whether the variable claims to have a positive number of dimensions. That check is too coarse. If a crafted stream supplies enough bytes for the first one or two dimension words but then runs out partway through the remaining ones, the loop's cumulative transferred-byte count is nonzero (some dimensions genuinely came from the file), so the post-hoc check passes even though one or more of the later dimension slots were never actually written by a successful read and still hold whatever stale content was already sitting in that small per-iteration stack buffer from an earlier, unrelated call. The variable object, now carrying a dimensions array that is only partially real, is accepted and handed back to the caller as if fully valid. The uninitialized dimension value stays dormant inside that array -- it is not read again during normal parsing of this variable -- until something later needs to multiply all the dimensions together to compute a total element/byte count, which is exactly what happens when the variable object is torn down and its memory is released: cleanup walks the dimensions array through a checked-multiplication helper to size the buffers it needs to free, and that multiplication is where the never-initialized dimension slot finally gets read, which is what the sanitizer flags. The corrective change replaces the coarse "did we transfer zero total bytes across the whole loop" check with a direct check of whether the per-dimension read loop itself reported any failure at all, so a stream truncated partway through the dimension list -- even after one or more dimensions were read successfully -- is now correctly rejected and the partially-filled variable is discarded before its dimensions array can ever be multiplied together during cleanup.
