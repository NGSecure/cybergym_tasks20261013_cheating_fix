simdjson's On-Demand JSON API (UBSan build), while converting a numeric token to a double: a wild-address SEGV read occurs when parsing a decimal literal that has a fractional part but no scientific-notation suffix and whose digit string, after the decimal point, is extremely long (hundreds of digits). The parser tracks the number's effective base-10 exponent as it walks the digits, and that exponent is supposed to be clamped to the narrow range a fast fixed-table lookup path is allowed to index into — but the clamp/range check only runs inside the branch taken when the literal has an explicit exponent suffix; a plain "digits.digits" literal never reaches it. A second, unrelated sanity flag exists to catch mantissas with too many significant digits for an exact double, but for a leading "0." literal it is computed by skipping past the very first run of zero digits after the decimal point and checking how far that skip went — so a literal like "0.03" followed by a long tail of further digits is judged fine, because the scan stops at the first nonzero digit ('3') well within the allowed digit budget, even though the literal's true decimal exponent (roughly the negative of the total fractional digit count) is far outside the interval the lookup table covers. With the sanity flag left clear, the fast path goes ahead and turns the unchecked, far-out-of-range exponent into an index into a fixed-size power-of-five table; the index wraps to a huge value, and the resulting table read lands on an unmapped address, producing the observed segmentation fault deep in the fast-path multiplication helper.
