libtiff crashes (MemorySanitizer use-of-uninitialized-value) while reading the RGBA pixels of a TIFF file whose image data is JPEG-compressed, when a crafted/malformed tile's embedded JPEG stream is fed through libtiff's bundled JPEG codec.

Root cause: TIFFReadRGBAImage -> TIFFRGBAImageGet -> gtTileContig asks the JPEG codec to fill a tile buffer; libtiff's JPEG glue layer forwards this to the underlying JPEG library's per-scanline decompression entry point. During header parsing for the tile's JPEG stream, the JPEG library allocates a per-component workspace buffer sized from the frame header (SOF marker) fields, but for this crafted input the tile's compressed data does not actually supply real coefficient values for that whole workspace before scanline output is requested. The routine that reconstructs full-resolution scanlines by borrowing coefficient rows from neighboring blocks (an interpolation/"smoothing" step used to approximate not-yet-fully-decoded rows near image edges) then reads directly out of that under-populated workspace as if it held real decoded DCT coefficients, propagating the uninitialized heap bytes into the output pixel row. No out-of-bounds access occurs — the read stays inside the allocated buffer — so this is purely an initialization-ordering bug between "buffer sized from header metadata" and "buffer actually filled with decoded coefficients", not a bounds or use-after-free issue.

fix_commit note: the recorded fix_commit (0f013e5b5a550606298fb50c3bb90920a7da76fc) is almost certainly unrelated to this crash. Its diff only touches libtiff's Windows-only file-I/O shim, changing the integer type used to read a file's size via GetFileSizeEx in the Windows stdio-replacement backend — it has nothing to do with JPEG tile decoding, the JPEG library's header parsing, or scanline reconstruction, and building/running the fuzz target on Linux never even compiles that file. This looks like a typical OSS-Fuzz day-granularity bisection artifact (the bisector landed on whichever commit happened to be built the day the reproducer stopped crashing, not the commit that actually addressed the bug) rather than a genuine fix for this uninitialized-value report.
