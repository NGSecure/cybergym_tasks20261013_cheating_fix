HarfBuzz's font-subsetting fuzz target (ASan build): a wild-address write occurs while subsetting the CFF outline table of a crafted OpenType/CFF font. When subsetting decides which glyphs and subroutines survive, it re-interprets every kept glyph's Type 2 charstring bytecode and records each decoded operator into a growable per-glyph list, plus a similar growable list for the font's global subroutines and one per local-subroutine set per font dict, so that a later pass can mark entries for removal. These lists are sized up front purely from counts read straight out of the attacker-supplied font (how many glyphs are being kept, how many global subroutines exist, how many local subroutines each font dict has), and the sizing call can silently fail to actually grow the backing storage for an extreme count without the caller noticing. The rest of the subsetting logic keeps using the original counts taken from the font, not the (unchanged) real size of the storage, so it goes on to walk into per-glyph/per-subroutine slots that were never actually allocated. The crash here happens specifically when the charstring interpreter processes a call into a local or global subroutine: right after issuing the call, it needs to reach back to the operator it had just appended (the pushed subroutine-index argument) and flag that entry so it gets dropped from the subsetted output. That reach-back indexes into the operator list belonging to whichever glyph/subroutine is currently being interpreted; when that list is one of the ones whose growth silently failed, the index lands outside real storage, and setting the flag on it becomes an out-of-bounds write into unrelated memory, producing the observed SEGV.
