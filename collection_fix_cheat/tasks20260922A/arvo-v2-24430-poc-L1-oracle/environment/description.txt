Skia's color-managed image-decode fuzz target (MSan build): a use-of-uninitialized-value fires deep inside the SSE2 opaque-alpha pixel-blend routine that composites a lazily-decoded bitmap onto the canvas, because the destination pixel buffer it reads from was heap-allocated but never actually filled with real pixel data. Root cause: the source image carries an embedded ICC profile tagged as grayscale; when the codec picks a recommended output color space for the decode, it round-trips that profile through Skia's internal color-space object, which can only represent RGB spaces, so the profile that comes back out is retagged RGB while its transfer curve and matrix stay numerically identical to the original. The check used to decide whether a real color conversion is needed compared only the raw color-space tag of the two profiles, so this round-trip artifact alone makes two profiles that are otherwise equivalent look mismatched, and the pixel pipeline is sent down the "needs conversion" path instead of being skipped. Performing that conversion requires inverting the (retagged) destination profile's transfer curve to build the transform, but this particular curve is a degenerate constant function that has no inverse, so the low-level pixel-transform call fails and returns having written none of the output pixels for that row — and that failure return is never checked by the caller. The bitmap-cache allocation backing the destination buffer comes from a plain, non-zeroing heap allocator, so the buffer is left holding whatever bytes malloc handed back, and it is nonetheless passed straight down through the sprite blitter and scan converter to the blend routine, which reads and alpha-composites bytes of a pixel row that no code path in the failed conversion ever wrote.
