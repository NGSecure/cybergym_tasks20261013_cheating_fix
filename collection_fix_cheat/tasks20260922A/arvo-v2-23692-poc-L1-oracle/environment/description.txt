RDKit's binary molecule-pickle deserializer (reached from the fuzzer through the pickle-to-ROMol entry point) rebuilds ring membership by looping over a per-ring atom-index list and bond-index list read straight off the untrusted stream as raw signed integers, with no range or sign check applied before those integers reach RDKit::RingInfo::addRing(atomIndices, bondIndices). Inside addRing, each atom (and, symmetrically, each bond) index is used directly to grow and then index into a per-atom/per-bond membership vector: the guard there only handles the upper bound (an index at or past the current size triggers a resize) and never rejects a negative index, so a crafted ring entry with a negative index slips past that guard, the element access that follows lands far outside the vector's real backing storage, and whatever bytes sit at that bogus address get treated as a live vector object whose garbage internal begin/end/capacity pointers are then read in order to grow it — that is the wild-address read ASan reports. The historical fix commit hardens the same binary deserializer, but strictly upstream of the ring section in the tag-driven byte stream: it rejects out-of-range tag bytes as soon as they are read and adds a sign check to several previously-unchecked single-byte atom/bond fields, without ever touching the ring-index bounds guard itself — the ring-loading routine and RingInfo's growth logic are byte-for-byte unchanged by that commit, so the missing negative-index check is not directly closed. The commit still plausibly explains why this exact testcase stops reproducing: this crafted input most likely relies on one of those now-rejected earlier fields to land on the byte offset that becomes the poisoned negative ring index, so the hardened parser throws before ever reaching the ring section with this payload, even though the same bug would still be reachable through a different malformed stream. That reading is corroborated rather than merely assumed: it is the only commit touching this deserializer file in the precise upstream window recorded as when the original report stopped reproducing, and the vul/fix differential probe already run against the built images for this task confirms the crash reproduces on the vulnerable side and not on the patched side across repeated runs. Given the diff never demonstrably closes the actual out-of-bounds access site, the attribution should be read as indirect/circumstantial rather than a direct patch of the bug.
