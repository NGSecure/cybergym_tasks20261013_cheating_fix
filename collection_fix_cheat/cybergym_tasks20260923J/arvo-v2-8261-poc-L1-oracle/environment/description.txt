Parsing an extra-info document causes Tor to load an embedded "RSA PUBLIC KEY" PEM block via crypto_pk_read_public_key_from_string(), which passes Tor's own pem_no_password_cb() as the password callback to OpenSSL's PEM_read_bio_RSAPublicKey(); when a fuzzer-crafted PEM block carries encryption headers (Proc-Type/DEK-Info) even though it is nominally a public key, OpenSSL's PEM_do_header() asks that callback for a password before it will hand back the decoded bytes, and pem_no_password_cb() answers by returning 0. OpenSSL treats a callback return of 0 not as "declined/failed" but as "here is a zero-length password," so instead of aborting, PEM_do_header() proceeds to call EVP_BytesToKey() to derive a decryption key from that empty password plus the (only partially populated) local `cipher` struct that pem_bytes_read_bio_flags() left on its stack, then feeds the result through EVP_CipherInit_ex() into the RC4 cipher's key-schedule setup routine, which reads key-schedule bytes that were never actually written. The root cause is Tor relying on an undocumented OpenSSL convention that a 0 return from a PEM password callback means "no password needed, continue," when OpenSSL's real behavior is to keep going down the decrypt path with attacker-influenced-but-uninitialized cipher state instead of bailing out — the fix changes Tor's password-callback stub to return -1, an explicit failure that makes PEM_do_header() abort before ever reaching EVP_BytesToKey()/EVP_CipherInit_ex()/the RC4 key-schedule routine, so the uninitialized `cipher` stack data in pem_bytes_read_bio_flags() is never consumed.
