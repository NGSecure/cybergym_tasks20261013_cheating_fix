ImageMagick's DICOM medical-image decoder (ASan build, exercised through a ping/metadata-only fuzz target): a heap-buffer-overflow read of a 4-byte value occurs while converting a decoded raw pixel sample into its display value for a non-indexed, non-JPEG-compressed image. Root cause: when the header-declared pixel bit depth differs from the library's native quantum depth, the decoder builds a small rescaling lookup table sized from that declared depth, falling back to a fixed, modest minimum entry count whenever the depth-derived size would otherwise be smaller. Later, when a decoded 8- or 16-bit pixel component is rescaled through this table, the code only checks that the raw sample value does not exceed the theoretical maximum representable value for whatever bit depth is in effect at that point in decoding -- it never checks the value against the table's actual allocated length. Because the depth used to size the table and the depth used to validate the lookup index are derived from attacker-controlled header fields and are not guaranteed to stay in lock-step (the depth in effect can be overridden to a different fixed value later in the same decode, e.g. for certain run-length-encoded multi-segment pixel layouts, without the earlier table being rebuilt at the new size), a crafted file can make the bounds check accept an index that is valid for the theoretical depth but falls outside the smaller buffer that was actually allocated, causing the lookup to read past the end of the heap allocation.
