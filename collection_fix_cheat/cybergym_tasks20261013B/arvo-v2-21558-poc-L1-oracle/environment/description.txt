One-sentence summary: gdal_translate crashes with a heap-buffer-overflow (out-of-bounds READ of 1 byte) while GDAL builds an internal overview for an NITF output using average-resampling on a color-table-indexed (paletted) raster band.

Crash mechanism: Inside GDAL's generic "average" overview resampler, each destination scanline first computes an integer source-row start offset from a floating-point ratio, then clamps that offset up to the current source chunk's top row if the computed value falls below it. The clamp is misapplied: it stores the clamped value into the wrong variable (a leftover double used only for weighting) instead of into the integer row-offset variable that is later reused. As a result, the integer row offset itself is never actually raised to the chunk's top row when it originally undershoots it.

Further down, the resampler unconditionally makes that row offset chunk-relative by subtracting the chunk's top-row value from it, expecting the offset to already be >= the chunk top (because of the clamp above). Since the clamp silently no-op'd on the integer variable, this subtraction can leave the row offset negative for the first destination scanline(s) of a chunk. That negative row offset is then used directly as the starting row index of the nested pixel-averaging loop in the paletted/color-table averaging branch, which reads source pixel values through a raw pointer into the source chunk buffer using `row_index * chunk_row_stride + col_index` addressing. A negative row index moves the read pointer backward past the start of the heap-allocated resampling chunk buffer, landing a few bytes before it -- exactly the "left of the allocated region" heap-buffer-overflow ASan reports.

This only manifests through the color-table (palette) averaging code path (i.e., when the source band being downsampled has an attached color table), not the plain numeric averaging path, and only for chunks/scanlines where the floating-point-to-integer row-offset rounding produces a value strictly below the chunk's starting row -- an edge case tied to the specific resampling ratio and chunk geometry rather than to any particular pixel content.

Fix: the clamp assignment was corrected to update the integer row-offset variable itself (instead of the unused double), so the row offset can never end up below the chunk's top row, which prevents the subsequent subtraction from going negative.
