muparser's expression compiler and bytecode evaluator (ASan build, reached through a string/expression-evaluation fuzz target) crash with a heap-buffer-overflow READ of 8 bytes. The crash is reached while evaluating a compiled expression that uses the ternary conditional operator, when a string-valued operand is placed directly in one of the operator's two branches (right after the "?" or right after the ":") instead of a numeric one, especially when such conditionals are nested inside each other. Before the fix, the tokenizer accepted a string literal in that position without restriction, so the compiler could produce a conditional bytecode sequence whose expected value-stack depth is inconsistent with what actually gets pushed and popped once a branch mixes string and numeric operands. When the interpreter later walks this bytecode, it keeps a running index into a heap-allocated value stack to pop the branch's condition value; with the miscounted bytecode this index can be driven one slot before the start of that array, so the read used to test the condition lands outside the allocation and triggers the heap-buffer-overflow. The fix makes it a syntax error for a string literal to appear directly after either conditional-operator token, so the malformed branch bytecode can no longer be produced; a debug-only bounds check was also added at the point where the interpreter pops the branch condition, as a secondary safety net.
