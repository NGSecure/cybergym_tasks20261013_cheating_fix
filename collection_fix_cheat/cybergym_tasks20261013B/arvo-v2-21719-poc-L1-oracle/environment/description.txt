One-sentence summary: nDPI's packet-processing entry point fails to validate that the captured packet buffer actually contains as many bytes as the IPv6 header's payload-length field claims before walking the IPv6 extension-header chain, letting that walk read past the end of the heap-allocated packet buffer.

Crash mechanism: when a packet's IP version indicates IPv6, the packet handler checks that the captured length covers the fixed IPv6 header, then reads the on-wire IPv6 payload-length field and uses it (unchecked) as the byte-length budget for a downstream helper that iterates the IPv6 extension-header chain. That helper trusts the caller to have supplied a length that matches real, addressable memory: for each extension header it is walking, it reads a next-header byte and a header-length byte from the current position and advances the pointer/remaining-length pair by the encoded extension-header size, looping until it hits a "no next header" terminator or runs out of the supplied budget. Because the caller never checked that the captured buffer is actually as long as the payload-length field claims, a payload-length value that overstates the real buffer size lets this loop keep walking (and dereferencing) past the true end of the allocated packet buffer once the real captured bytes are exhausted, producing a 1-byte heap-buffer-overflow read. The crashing dereference is a byte read used to compute the size of an IPv6 extension header while iterating the chain.

Fix: the caller now checks that the captured length also covers the full declared IPv6 payload (header size plus the on-wire payload-length field), in addition to the header-only check, before handing the length off to the extension-header walker; if the buffer is too short for the declared payload, the packet is now rejected before the walk begins. A now-redundant write-back of the resolved next-header value into the original header field was also dropped, but the buffer-coverage check is the actual root-cause fix.
