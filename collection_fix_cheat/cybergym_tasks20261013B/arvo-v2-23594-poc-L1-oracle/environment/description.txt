njs (the nginx JavaScript engine) script-processing fuzz target crashes with a wild-address SIGSEGV while tearing down function call frames right after a native (C-implemented) builtin function returns during bytecode interpretation. Root cause: the interpreter's native-call-return path treats the compact call-frame record used for calls into native functions as if it were the larger record used for frames of interpreted (user-defined) JS functions, so it writes a return-value bookkeeping slot at a byte offset that is only valid in the larger layout -- an offset that sits just past the true end of the compact record. This write stays harmless for as long as the compact record's actual allocation still carries a few bytes of trailing alignment padding wide enough to absorb it, so the bug is latent rather than reliably crashing; but that safety margin is fragile, since it depends on the exact byte size of an unrelated struct staying just under an alignment boundary. Once that struct grows enough to consume the padding, the same misplaced write instead lands past the record's real allocation boundary and clobbers bookkeeping belonging to whatever memory follows it -- corrupting the pointer used to chain back to the previous active call frame. The very next step after a native call returns walks that chain to release completed call frames, and it dereferences the now-corrupted link, following it into an unmapped/invalid address, producing the observed out-of-bounds wild-pointer read and crash.
