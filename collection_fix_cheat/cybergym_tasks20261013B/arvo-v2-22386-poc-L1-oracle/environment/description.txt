llvm-isel-fuzzer / LLVM IR CFG-simplification pass: heap-use-after-free (4-byte READ) while folding several predecessor edges into a shared `resume` landing-pad block.

Mechanism: the pass merges predecessor edges into the shared resume block one predecessor at a time, and after handling each predecessor it asks the target block to drop that predecessor so the block's PHI nodes stay consistent. That predecessor-drop helper walks the block's PHI nodes and trims one incoming value from each; if trimming an incoming value leaves a PHI node with no further useful incoming edges, the trim operation itself deletes the PHI node as an implicit side effect, folded into the very call that trims the value — nothing signals back to the caller that the node was destroyed. The optimizer's outer loop over the remaining predecessors keeps referring to the same PHI node across iterations (it needs to read the node's current operand count to locate which slot corresponds to a given incoming block), assuming that node is still live for the whole multi-predecessor merge. Once an earlier iteration's predecessor-drop call happens to trim the node down to nothing and free it, a later iteration's lookup on that same node dereferences already-freed heap memory: ASan shows the free and the use inside the very same enclosing routine, with the free call one source line after the read call, which only makes sense if the read call is re-executed on a later pass through the loop after an earlier pass already triggered the free — i.e. free-then-stale-reuse, not the reverse.

Fix: the predecessor-drop helper's PHI handling was restructured so destruction of a PHI node is no longer an implicit, uncontrolled side effect of trimming one incoming value. The "only one incoming edge will remain after trimming" case became its own explicit branch that removes the node from the block's instruction list directly and once, instead of relying on the trim step to notice the node emptied out and silently erase itself; and for blocks that still have more incoming edges left, the trim step is now explicitly told not to self-delete the node even if trimming would otherwise leave it empty, so any deletion happens later at one well-defined point instead of hiding inside the trim call. That closes the window where a node the outer merge loop still expects to dereference on a later iteration could vanish out from under it as an unadvertised side effect of an earlier iteration's trim.
