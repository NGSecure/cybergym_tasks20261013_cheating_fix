mruby (ASan build): executing an indexed array-assignment expression with an out-of-range, extremely large index forces the interpreter to grow the target array's backing storage to a correspondingly huge byte count; the allocator refuses a request of that size, so the growth attempt fails. Root cause: on that failure path, the interpreter frees the array's original backing buffer and then raises a "no memory" exception, but it never clears or otherwise invalidates the array object's own pointer to that buffer, so the array is left referencing already-freed memory even as the exception unwinds the call stack and the script aborts. When the interpreter later shuts down, its garbage collector's final sweep over all remaining live heap objects walks this same array and frees its backing buffer a second time, producing a heap double-free of an allocation that had already been released once during the earlier failed grow.
