Skia (MemorySanitizer build, image_filter_deserialize_width fuzz target) reports a use-of-uninitialized-value while deserializing a filter/picture stream that embeds a custom-vertices (mesh) object: as the vertices header is decoded, each declared per-vertex attribute's numeric type tag and usage tag is checked to be individually within its own valid enum range as it comes off the wire, but nothing at that point checks whether a given type/usage pairing is actually a legal combination for that attribute (e.g. some usages only make sense paired with certain value types, and one usage requires that no optional name string be attached). A small internal helper walks the decoded attribute list to compute the eventual object's total allocation size and to report whether that computation succeeded, and it bails out immediately the moment it hits an attribute whose type and usage are each individually in-range yet mutually incompatible - but that early exit happens before the helper ever sets the one field its caller relies on to know whether the computation actually succeeded. The caller then branches on that field to decide whether to keep building the vertices object or reject the input, so it ends up reading a stack slot that was never written on this path, and MemorySanitizer flags that read as a use of uninitialized memory.
