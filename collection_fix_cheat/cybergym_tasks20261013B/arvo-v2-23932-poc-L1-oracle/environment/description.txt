Skia's SVG-canvas output backend (MSan build): while emitting `<defs>` resources for a drawn path, the SVG device asks whatever shader is attached to the paint to describe itself as a gradient, so that even a plain solid color can be represented as a one-stop gradient in the generated markup. Making that query triggers a use-of-uninitialized-value warning. Root cause: right before the query, the caller stack-allocates a small info struct that will receive the shader's answer, but it only sets the struct's color-count field (to zero, signalling "just tell me the type/count for now") -- the struct's separate colors-array pointer field is left holding whatever garbage bytes were already on the stack. The plain-color shader's implementation of the query, however, guards its one write to that struct with two conditions checked together: a non-null test on the colors-array pointer field, and a check that the count field is at least one. Because it is the pointer field's still-uninitialized bytes that get consumed while that combined guard is evaluated and acted on -- as part of the very statement that would conditionally store a color through the pointer -- MemorySanitizer's origin trace follows the uninitialized value straight back to the stack frame where the info struct was declared in the SVG device's resource-emission helper. The upstream fix replaces the caller's single-field initialization with a full zero-fill of the entire info struct before the query, so every field (not just the count) starts out well-defined; with the pointer field now guaranteed to be a real null on this first, count-only query, the shader's guard is unambiguously false and the code path that reads/writes through the pointer is never taken.
