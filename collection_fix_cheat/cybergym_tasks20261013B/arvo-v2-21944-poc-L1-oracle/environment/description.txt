Oniguruma's regex-pattern parser supports numeric code-point escapes that let a pattern author specify an arbitrary character by its raw integer value rather than by literal bytes. When the parser encounters such an escape, it must convert that numeric value into the pattern's configured multi-byte encoding before folding it into the compiled node tree, and doing so correctly requires first checking whether the value is actually a legal, representable character under the target encoding, since not every integer corresponds to a valid character in every multi-byte encoding's table. For certain variable-width CJK encodings, this legality check and the actual byte-encoding step are two logically separate operations, and an order-of-operations bug lets the parser skip straight to encoding an out-of-range value onto a small fixed stack buffer before that value has ever been validated. For some invalid values, the byte-writing routine only fills in a subset of that stack buffer's bytes, leaving the remaining bytes holding whatever was already sitting on the stack. The encoding's own length-detection routine is then invoked to figure out how many bytes were written, but for these particular byte patterns it needs to inspect one of the bytes that was never actually written to disambiguate a short encoding from a longer one, so it ends up reading uninitialized stack memory. Because this entire sequence happens purely while compiling the pattern itself, no search against any subject string is required to trigger it: MemorySanitizer flags the read as a use of an uninitialized value during pattern compilation, before matching ever begins.
