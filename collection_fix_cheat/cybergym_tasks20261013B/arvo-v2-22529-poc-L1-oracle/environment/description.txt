PcapPlusPlus's TLS/SSL handshake parser, after successfully getting past a ServerHello message's session-ID and cipher/compression fields, enters a loop that walks the list of TLS extensions appended to the rest of the handshake message, decoding each extension's declared length by reading two bytes at the current parse position. Root cause: the loop's exit condition only checks that the parse position hasn't yet reached the extensions-length or overall-message boundary before decoding the next extension entry -- it never separately checks that a full extension header still fits within the bytes remaining -- so a ServerHello whose extension list is truncated right where one more (partial) extension header would begin causes that length read to run past the end of the same underlying packet buffer, a heap-buffer-overflow read that is mechanically distinct from (and unreachable by) the shorter-message case that trips the session-ID-length read earlier in the same message type's construction.
