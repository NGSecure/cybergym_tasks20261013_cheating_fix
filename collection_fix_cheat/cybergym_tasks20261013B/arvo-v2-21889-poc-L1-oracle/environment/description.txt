GDAL's OGR WAsP vector driver opens a data source by treating one of its header lines as a PROJ4-style coordinate-reference-system string and handing it to OGRSpatialReference::importFromProj4(), which forwards it into PROJ's generic string-init path (createFromUserInput() -> PROJStringParser::createFromPROJString() -> pj_create_argv_internal() -> pj_init_ctx_with_allow_init_epsg()). When that string describes a "+proj=pipeline" definition, PROJ's pipeline setup routine walks each step of the pipeline and, for a step that itself resolves to another pipeline definition, re-enters the very same string-init call chain to initialize that nested step. This re-entry is a plain function-call recursion with no depth counter or any other bound on how many times it may nest: a projection string that is quoted or escaped so that a pipeline step ends up textually containing another "+proj=pipeline" step (directly or through several layers of nesting) makes the initializer call itself over and over, one stack frame per nesting level, before it ever gets to doing real projection setup work. Given enough nested pipeline steps, this unbounded init-time recursion exhausts the calling thread's stack. The process does not crash where the nesting first happens; the crash surfaces a bit later, when the exhausted call stack finally causes PROJ's own error-logging path (proj_log_error() -> pj_vlog(), which formats a message via the C library's vsprintf()) to write past the end of the stack region entirely, producing a wild-address write and a SIGSEGV instead of a controlled error return. Root cause: the pipeline-step initializer in PROJ (as vendored into GDAL) had no limit on how deeply a "+proj=pipeline" definition could reference further pipeline definitions, so a self-nesting projection string alone -- independent of any buffer-size or arithmetic bug -- was enough to drive the initializer into unbounded recursion and blow the stack.
