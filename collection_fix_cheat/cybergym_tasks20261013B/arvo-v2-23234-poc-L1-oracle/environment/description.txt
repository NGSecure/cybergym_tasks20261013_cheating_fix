stb's PNG decoder (exercised by the stbi_read_fuzzer harness under a MemorySanitizer build) reports a use-of-uninitialized-value read while expanding a low-bit-depth indexed-color (palette) scanline into full pixel output during PNG decoding.

Root cause: for a palette (color-type 3) image whose declared bit depth is below 8 bits per index, the raw-scanline unpacking step computes how many bytes each decoded row should occupy from the image's stated width and bit depth, but only checked that computed size against the actual per-scanline byte budget with a debug-only assertion rather than a real error path -- a check that is compiled out entirely in the release/fuzzing build. When the zlib/deflate stream backing the PNG's compressed image data is truncated, corrupt, or otherwise fails to supply as many decompressed bytes as the header promises, the inflate/huffman routine can return early, leaving the tail of its heap-allocated output buffer holding leftover bytes from the original allocation rather than real decoded pixel data. Because the missing bounds check no longer catches the width/byte-count mismatch this shortfall produces, the row-unpacking step proceeds anyway and treats that partially populated buffer as fully valid. The subsequent palette-expansion pass then walks every byte of that index buffer to look up the corresponding output color, unconditionally reading past the point where real decoded data ends and into the never-initialized tail of the buffer -- which is what the sanitizer flags. No out-of-bounds access occurs; this is purely an uninitialized-heap-memory read whose value would silently leak into the decoded pixel output if it reached the caller.
