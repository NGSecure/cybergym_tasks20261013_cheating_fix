A heap-buffer-overflow WRITE of 4 bytes occurs in RDKit's chirality/CIP-rank refinement routine, invoked while parsing an MDL Molfile/SDF record to assign atom chirality codes. That routine keeps one growable integer vector per atom and seeds each vector with exactly two entries (the atom's atomic number and its initial tie-rank) through two back-to-back appends, so the underlying heap allocation for each seeded vector holds room for precisely those two integers and nothing more.

On every refinement round the routine collects each atom's sorted neighbor-rank/attached-hydrogen data and appends it to that atom's vector, then, in one shared pass over all atoms, pads every atom's vector up to whatever the longest vector produced this round happens to be, before finally writing this round's freshly computed rank value into each atom's vector at an index equal to the current round counter (and trimming the vector back down to that same length). This padding step is the only thing that ever grows a vector past its two-entry seed.

The refinement loop keeps iterating as long as two or more atoms still share the same rank. If a later round arrives where none of the atoms in the molecule can contribute any new neighbor/hydrogen information that round (for example, an atom left with no remaining bonds and no attached hydrogens to describe), the "longest vector produced this round" value never exceeds the two-entry seed size, so the padding step does nothing for anyone, yet the rank write at the round-counter index still executes unconditionally for every atom. For any atom whose vector is still only two integers long, that write lands one 4-byte integer past the end of its 8-byte heap allocation, corrupting whatever heap memory follows it — matching the observed heap-buffer-overflow write.

Note on fix relevance: the upstream commit recorded as this crash's fix only adds a large, separate, opt-in CIP-labeling module and wires it up as an additional import; a byte-for-byte comparison of the vulnerable refinement routine between the vulnerable and "fixed" source trees shows it is completely unchanged (only relocated within the file). The default molfile-parsing code path that reaches this routine is untouched, so this recorded fix commit does not itself patch the described root cause.
