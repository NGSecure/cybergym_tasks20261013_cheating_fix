Oniguruma's case-insensitive matcher compares a candidate substring of the search subject against a fixed-length literal from the compiled pattern by case-folding both sides one encoded character at a time and comparing the folded output bytes, advancing each side's cursor by however many source bytes that character's case-folding step actually consumed. The loop driving this comparison only checks whether the pattern-literal side has reached the end of its declared span; it never separately checks whether the subject-string side's cursor has already reached the end of its own, equally-sized span. Because a single case-folded output does not always consume the same number of input bytes on both sides — a multi-byte character can fold from (or into) a representation of a different byte length than the character it is being compared against — the subject-side cursor can be pushed past the end of its span during one iteration while the pattern-literal side has not yet reached its own end. The loop then continues into another iteration, invoking the case-folding step one more time on the subject side using a pointer that already sits one or more bytes past the boundary of the heap buffer holding the subject string, and that pointer gets dereferenced. AddressSanitizer reports this as a small heap-buffer-overflow read. Unlike a defect that surfaces purely from parsing a pattern, this one can only be observed once a compiled pattern using case-insensitive matching is actually run against a subject string via a search call, at a match position where the two sides' case-folded byte-consumption has drifted out of lockstep near the end of the compared span.
