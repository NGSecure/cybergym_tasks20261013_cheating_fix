Parsing a malformed MDL/SDF V2000 molfile can trigger a 1-byte out-of-bounds stack read (AddressSanitizer stack-buffer-overflow READ) inside the code path that handles legacy pre-V2000 "atom list" records embedded right after the atom/bond block of a mol block.

Root cause: once the V2000 reader finishes the atom and bond blocks, it peeks at the next line of the properties section before entering the normal property-line loop. If that line's first character is not one of a small set of letters that mark a recognized modern property directive, the reader assumes the line is an old-format atom-list record and hands the entire raw line straight to a dedicated legacy-atom-list handler, with no check on the line's length. That handler first extracts a numeric atom index from the start of the line (safe, since it uses a bounds-clamping substring read), then inspects a single character a few bytes further into the line to decide whether the list is negated ("T"/"F" for a NOT-list flag). When that character is anything other than those two expected values, the code falls into an error-reporting branch that builds a diagnostic string meant to quote "the unrecognized character" for the error message — but the diagnostic reads the character from a fixed index roughly ten bytes further into the same string than the character that was actually just examined by the T/F check, instead of re-using that same index. For a short properties-block line that is long enough to reach the T/F check but too short to reach that much later, unrelated index, the diagnostic's read runs past the end of the line's underlying character storage. Because the string is short enough to live in the caller's stack frame (small-string optimization), AddressSanitizer reports this as a stack-buffer-overflow of size 1.

In short: this is a copy-paste/off-by-a-large-constant indexing bug confined to the error-message-formatting branch of the legacy atom-list parser, not the primary numeric-parsing logic — it is only reachable when the fuzzer-supplied input is malformed enough (a short line, not starting with a recognized directive letter, whose flag character is neither of the two accepted values) to fall into that particular error path.
