A MemorySanitizer use-of-uninitialized-value bug in LLVM's SCCP (Sparse Conditional Constant Propagation) middle-end optimization pass, reached through the llvm-opt-fuzzer harness running the sccp pass over an arbitrary IR module. While processing a PHI node, the solver merges the abstract lattice values coming from the node's feasible incoming edges into one combined lattice state, then re-reads that state's internal step counter (a small bit-field used to cap how many times a constant-range value may be "widened" before the solver gives up and marks it overdefined) and folds it together with the count of active incoming edges via std::max — and that counter turns out to still hold whatever garbage bytes were already sitting in memory. Root cause: the lattice-element type's default constructor, and its copy/move constructors, only ever initialize the discriminant tag (unknown/undef/constant/notconstant/overdefined/constant-range) plus, for the constant-range variant specifically, the range payload and its step counter; for every other tag value they leave the step-counter field completely untouched. Because these lattice elements live inside a hash map whose backing storage is a plain heap allocation (not zero-filled), any element that is default-constructed, or copy/move-constructed from a source that is not itself in the constant-range state, ends up with that counter holding indeterminate bytes rather than zero. As long as the element is only ever read through operations that ignore the counter, nothing goes wrong; the bug only surfaces once code explicitly reads the counter off a lattice element that never took the constant-range path. The fix adds an explicit zero-initializer for that counter to the member-initializer list of the default, copy, and move constructors, so every newly constructed or copied lattice element has a well-defined counter value regardless of which tag it ends up with, while the constant-range-specific branches still go on to overwrite it with the real widening count where applicable. This directly closes the gap being exploited here: it guarantees the exact field the solver later folds via std::max is never read before being written.
