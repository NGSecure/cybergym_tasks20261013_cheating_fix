leptonica's in-memory BMP image reader (ASan build, exercised via the rotate/shear fuzz target's generic pixReadMem entry point): a heap-buffer-overflow read of roughly 196 bytes occurs, landing just before the start of the input buffer rather than past its end. Root cause: the BMP info-header's own declared byte length (a field the format lets vary across historical header revisions) is taken directly from the untrusted input and used, unvalidated, both to compute how many palette/colormap entries follow the header and to compute the byte offset of where that palette data begins within the buffer; the code checks that the *end* of the palette region lines up with the file-header's separately-declared data offset, but never checks that the header-length field itself is one of the handful of values BMP headers actually come in. A crafted file can therefore make that field evaluate as a small or effectively negative quantity, which simultaneously inflates the derived palette-entry count and shifts the copy source pointer backward past the buffer's start, so the subsequent bulk copy of "palette" bytes reads out of bounds behind the allocation instead of the well-formed region the size check was meant to guarantee.
