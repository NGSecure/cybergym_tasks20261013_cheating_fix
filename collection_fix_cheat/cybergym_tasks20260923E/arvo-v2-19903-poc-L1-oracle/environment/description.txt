The same LABEL-coder / FX-expression evaluation path is involved as in the sibling crash on this project, but this is an independent defect: here a keyword-style pseudo-function IS correctly recognized as a genuine invocation (it really is followed by an opening delimiter), so the misclassification bug from the sibling case cannot be the cause. Instead, the bug lies in how the recognized keyword's own argument text is parsed: several distinct keyword handlers inside the FX expression-evaluation routine each copy the substring between the keyword's delimiters into a fixed-size scratch buffer using a bounded string-copy helper that returns how many bytes were actually copied, then unconditionally overwrite the byte at "copied length minus one" with a NUL terminator to close off the copy -- without first checking whether the copy produced any bytes at all. When the keyword's argument content is empty or degenerate, the copy returns a length of zero, and computing "length minus one" as an unsigned count wraps around to a very large value, so the terminator write lands one byte before the start of the scratch buffer (AddressSanitizer reports a 1-byte WRITE heap-buffer-underflow). Several of these keyword handlers share the identical unguarded-decrement pattern; the crash observed here is reached through a deeply nested expression -- recursing through operator-precedence parsing, a bracketed symbol lookup, and a further nested operator -- that funnels evaluation into one specific instance of it.
