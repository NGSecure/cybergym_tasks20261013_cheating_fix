This is a heap out-of-bounds read in the driver that decodes a security-token vendor's proprietary object format inside opensc's smart-card enumeration path. On-card objects are cached in a per-identifier table the first time each one is fetched: a byte buffer is allocated to exactly the size the object's length field claimed at that moment, filled with the bytes actually read from the card, and attached to whichever table entry a lookup-by-identifier happens to return. Nothing prevents the same object identifier from appearing more than once in this table with different declared lengths -- one entry might carry a small length from an earlier, minimal registration of that identifier, while a later, fuller registration of the same identifier records a larger length without ever being reconciled against the first. Because caching is keyed purely by identifier and short-circuits once any data is already attached, a lookup that resolves to the small, already-cached buffer can still be paired with a table entry whose currently-recorded length is the larger value from a different registration of the same identifier. Here the driver reaches this mismatched state while fetching a single scalar, integer-typed attribute directly by identifier -- for instance while reading an object's class or key-type value during ordinary card enumeration -- rather than while walking a certificate's attributes on the way to matching it against a key. It trusts the larger, mismatched length as the true remaining size of the buffer and uses it to decide whether enough bytes are left to safely read the next attribute record's small fixed header. Believing more bytes remain than the small cached allocation actually holds, it reads one field near the end of that header anyway, walking a few bytes past the end of the real allocation. Because reaching this state only requires a real token to present the same object identifier through more than one of the enumeration mechanisms the driver already supports, with different declared sizes each time, no protocol-illegal or otherwise unrepresentable card response is needed -- an internally inconsistent but individually well-formed pair of responses for the same identifier is sufficient.
