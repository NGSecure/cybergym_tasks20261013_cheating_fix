This is a heap out-of-bounds read in the driver that decodes a security-token vendor's proprietary object format inside opensc's smart-card enumeration path, specifically in the legacy (version-0) variant of that on-card object encoding. On-card objects are cached in a per-identifier table the first time each one is fetched: a byte buffer is allocated to exactly the size the object's length field claimed at that moment, filled with the bytes actually read from the card, and attached to whichever table entry a lookup-by-identifier happens to return. Nothing prevents the same object identifier from appearing more than once in this table with different declared lengths -- one entry might carry a small length from one enumeration path the driver supports, while a different enumeration path registers the same identifier again with a larger length that is never reconciled against the first. Because caching is keyed purely by identifier and short-circuits once any data is already attached, a lookup that resolves to a small, already-cached buffer can still be paired with a table entry whose currently-recorded length is the much larger value left over from a different registration of the same identifier.

Later, when the driver needs to know how many legacy-format attribute records follow a given object, it first checks that the object's currently declared remaining length is bigger than the fixed legacy object header, then reads a two-byte "how much attribute data follows" field placed near the very end of that header in order to start walking the attribute list. Trusting the mismatched, oversized declared length lets that size check pass even though the buffer actually cached for this particular object is only a single byte long, so the two-byte field read lands several bytes past the end of the real allocation.

Because reaching this state only requires a real token to present the same object identifier through more than one of the enumeration mechanisms the driver already supports, with different declared sizes each time, no protocol-illegal or otherwise unrepresentable card response is needed -- an internally inconsistent but individually well-formed pair of responses for the same identifier is sufficient to trigger the bug.
