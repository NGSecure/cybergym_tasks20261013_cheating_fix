This is a heap out-of-bounds read in the generic routine that copies a requested attribute's value out of an on-card object's already-parsed record data during opensc's enumeration of a proprietary-format smart-card token's contents into its internal PKCS15 view. Each on-card object the driver has discovered is represented by a table entry carrying both a byte buffer holding that object's raw record data (fetched from the card and cached the first time anything asks for it) and a companion field recording how many bytes that buffer holds. When any part of the pkcs15 emulation layer asks for a specific attribute of a given object -- its identifier, its value, a boolean or numeric property, or similar -- the driver locates the buffer already cached for that object, fetching and caching it fresh if this is the first request, then walks the fixed-format attribute records packed inside that buffer using the entry's own recorded byte count as the bound that keeps the walk from running past the end, extracts the matching record's declared value length, and copies that many bytes into the caller's destination.

This scheme depends on the recorded byte count on a table entry accurately describing the buffer that is actually cached under that same entry. The two are populated together the first time an object's data is fetched and cached, and are meant to stay in lockstep from then on. But the driver's internal notion of "the object with this identifier" is not perfectly single-valued: the same underlying on-card object can be looked up again by identifier through more than one route as the driver works through a token's proprietary object stream over the course of a normal enumeration pass, and nothing guarantees that a repeated lookup for a given identifier consistently resolves back to the one table entry whose buffer and byte count were originally paired together at the time they were first cached.

When a later lookup for a given identifier lands on a table entry whose already-cached buffer belongs to what the driver had, at some point, treated as a different reference to the object, and the byte count now recorded against that entry is larger than that particular cached buffer really is, the record walk -- and the value-length-bounded copy it performs once it finds the matching attribute -- both trust the larger recorded figure and read well past the end of the real, smaller allocation. Nothing about a token driving the driver's internal identifier-to-entry mapping into this state, across the different ways the driver is willing to re-resolve one identifier during enumeration, requires any single response to look malformed on its own, so a nonstandard or adversarial token can reach it while still producing individually well-formed responses at every step.
