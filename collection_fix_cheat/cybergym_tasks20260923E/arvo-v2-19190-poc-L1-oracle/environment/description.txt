This is a heap out-of-bounds read/copy in the driver that decodes a security-token vendor's proprietary object format inside opensc's smart-card enumeration path, triggered while assembling one of the token's public-key objects. As the driver walks the token's object directory, it appends every object entry it sees to an in-memory table keyed by a 4-byte identifier the token supplies, and nothing rejects a second entry that reuses an identifier already present in the table even if that second entry declares a different byte length than the first. The first time any entry for a given identifier is actually read from the token, the driver allocates a buffer sized to exactly that entry's own declared length, fills it with the bytes read back, and then stores the resulting pointer on whichever table entry a plain identifier lookup happens to return -- not necessarily the specific entry that triggered the read. When two entries share one identifier with different declared lengths, that lookup can resolve to either of them, so the buffer ends up attached to a table entry whose own recorded length disagrees with the buffer's true allocated size. A later, unrelated fetch of a large byte-string attribute (the kind used to carry a public-key component while building the key object) for that same identifier finds the entry already has data cached, skips allocating anything fresh, and instead mallocs a brand-new output buffer sized to the entry's own (possibly much larger) declared length before copying that many bytes out of the small, real cached buffer -- reading and copying well past the end of the actual allocation. Because the token's whole object directory and object payloads are attacker/fuzzer-supplied bytes with no cryptographic integrity check at this layer, producing two internally-plausible, individually well-formed directory entries that happen to share an identifier but disagree sharply in declared length is entirely sufficient to reach this state; no protocol-illegal response is required.
