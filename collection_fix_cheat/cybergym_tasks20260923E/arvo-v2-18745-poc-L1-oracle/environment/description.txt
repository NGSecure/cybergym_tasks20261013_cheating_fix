This case again goes through the full document-rewriting path with a malformed input PDF (its cross-reference table is likewise unusable and gets reconstructed), and the embedded image stream it touches is corrupt enough that the JPEG decoder initially rejects it outright, the surrounding logic retries, and only a partial/recovered decode completes. The key difference from the other document-rewriting case is what happens to the decoded pixels next: instead of passing the still-compressed image bytes through largely as-is, this path fully decodes the image to raw samples and immediately feeds those raw bytes into a second, general-purpose lossless compressor to produce a replacement stream. That second compressor does not just copy its input byte-for-byte; it maintains a sliding lookahead window over the data and searches it for repeated byte sequences before deciding how to encode each position, and it is specifically the step that refills/extends that lookahead window from the sample buffer -- reaching further ahead into the buffer than a simple sequential copy would -- that first touches bytes the sanitizer still considers not-yet-written. The distinguishing mechanism here is not "decode produces a partly-uninitialized block" by itself (that part is shared with the other document-rewriting case) but that the specific downstream consumer is a match-searching compressor whose window-fill logic reads ahead of what has actually been produced, rather than a straight measure-and-copy of the decoded bytes.
