Open vSwitch's datapath flow-action fuzz target round-trips a textual flow-action string into user-space, Netlink-encoded flow-key attributes and then formats those in-memory attributes back into text for display/logging; a heap-buffer-overflow read of one byte occurs during that display pass. Root cause: one of the flow-key attribute kinds supports a repeated sub-field (used for tunnel-encapsulation options, where a caller can list the same kind of sub-value many times); when enough repetitions are supplied that the attribute's total encoded size grows past what its 16-bit length header can represent, the routine that finalizes the attribute writes the now-truncated (silently wrapped-around) size straight into that header, with no check that the true size actually fit. The header therefore ends up recording a length far smaller than the attribute's real extent inside the backing buffer, while the buffer itself still holds every byte that was actually written. Later, the code that walks the buffer to enumerate attributes trusts each header's declared length to locate where the next attribute begins; because the finalized attribute's declared length is now wrong, the walk concludes that attribute ended early and re-interprets real, still-valid payload bytes immediately following it as the header of a brand-new attribute. Whatever bogus type/length happens to fall out of misreading those payload bytes as a header can claim a payload that runs past the buffer's actual allocation, and when the formatter subsequently dumps that bogus "attribute"'s raw bytes one at a time for the log/debug string, the read walks one byte beyond the end of the heap allocation.
