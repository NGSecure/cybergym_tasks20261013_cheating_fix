This is a double-free in the code that decodes a PKCS#15 public-key directory-file entry from raw card data. Each such entry carries a nested ASN.1 CHOICE whose payload — depending on the key algorithm the entry declares (RSA, EC, DSA, GOST) — either embeds a path reference or, for at least two of the algorithm branches, an inline octet-string blob that the ASN.1 decoder allocates a fresh heap buffer for and hands back through an out-parameter pointer/length pair. That same pointer/length pair is not a local, throwaway variable: it aliases a field on the public-key object being built, the object's generic "raw content" buffer that every PKCS#15 object type shares and that the object's own destructor later frees as part of normal list teardown, using whatever pointer and length are currently recorded there.

The entry decoder runs the whole nested ASN.1 structure through one decode call and then branches on the outcome. On a negative return — meaning parsing failed partway through, which can happen after the octet-string sub-decode already ran and populated the object's content pointer — an error-handling branch that a since-reverted "fix memory leaks" change had added explicitly frees that content pointer, on the theory that the decoder wouldn't otherwise release memory it had already allocated for an entry that's about to be discarded. That reasoning was wrong on two counts: first, the decoder's own error path already releases entries it allocated earlier within the same failed decode call, so the buffer may already be gone by the time this branch runs; second, even when the buffer is genuinely still live at that point, the branch frees it but never clears the object's recorded pointer or length back to empty. Either way, execution then falls through to the function's own error label, leaving the object linked into the pkcs15 card's object list with its content bookkeeping still describing a buffer that is either already freed or about to be freed here for the first time — but in neither case is the bookkeeping updated to reflect that.

Later, when that object list is torn down — the normal per-object cleanup that runs whenever a pkcs15 card structure holding a malformed or only-partially-decoded object is released — the shared object-content-release helper sees a non-null pointer with a non-zero length still recorded on the object, exactly as if the buffer had never been freed, and releases it again. The second release lands on memory that was already handed back to the allocator by the decode-failure branch, corrupting the heap allocator's free-list bookkeeping. No unusual API sequencing or multiple pointers into the entry is required — a single directory-file entry whose algorithm choice is one of the ones with an inline octet-string payload, followed by any later ASN.1 failure elsewhere in that same entry's structure (so the decode call returns an error status other than the harmless end-of-contents one), is sufficient to reach this state through the card's completely ordinary public-key-directory-parsing path.
