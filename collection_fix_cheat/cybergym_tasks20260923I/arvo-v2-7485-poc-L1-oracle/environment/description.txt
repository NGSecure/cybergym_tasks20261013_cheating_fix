A bug in ImageMagick's PIX raw raster-image decoder (MSan use-of-uninitialized-value) occurs while reading a crafted PIX file. The reader establishes the destination image's pixel storage (a fresh, unzeroed heap allocation sized to the declared dimensions) and separately builds a colormap for the image, then later synchronizes every pixel against that colormap by converting each pixel's raw channel values into a colormap index and writing that index back into the image. For certain crafted inputs, the raw per-pixel sample data isn't actually decoded and written into the destination pixel storage before this colormap-synchronization pass runs — the storage was only ever sized, never populated for those pixels — so the index-computation step ends up reading straight from never-written heap memory when it looks at the pixel's channel values.

The fix adds an explicit step immediately after the pixel storage is sized (and gates it on that sizing call actually succeeding) that resets the whole pixel storage to a defined baseline value before anything else touches it, so a pixel that the decode loop doesn't happen to reach for whatever reason no longer contributes indeterminate memory to the colormap-index computation.

fix_commit plausibility: highly plausible: the diff inserts the reset call directly after the pixel-storage-sizing call in the exact reading routine that sits at the bottom of the crash's own allocation-origin stack frame, and the crash itself is precisely a downstream consumer (the colormap-index push during synchronization) reading a pixel value that was never actually decoded.
