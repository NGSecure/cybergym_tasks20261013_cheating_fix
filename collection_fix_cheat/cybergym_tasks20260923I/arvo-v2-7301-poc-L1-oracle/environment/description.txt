A bug in ImageMagick's MVG arc-primitive renderer (ASan heap-buffer-overflow WRITE, size 8, "far from bounds") occurs while pinging a crafted MVG document that draws an "arc" primitive. Before the tracing routine walks an arc and writes out its interpolated points, the renderer must first estimate how many points that walk will actually produce, so it can size the shared points buffer accordingly. The estimation code, however, treats the "arc" primitive exactly the same as a "circle" primitive for this purpose — reusing the circle case's own geometry interpretation of the primitive's stored coordinate points (which describes a circle's center and radius) even though an arc's stored points describe a different shape entirely. Because that geometry interpretation is wrong for the arc case, the coordinate-count estimate doesn't correspond to how many points the arc actually gets subdivided into during tracing, and for a crafted arc/angle-span combination the real tracing walk writes points well past the end of a buffer sized for the wrong shape.

This sample reaches the same underlying defect through the metadata-only "ping" path rather than a full decode, with a much larger destination buffer (roughly 2.5 million entries) than the sibling sample on this project's write landing 8 bytes past the buffer's very end rather than colliding with unmapped memory outright — the same missing arc-specific size estimate, exercised by a differently-shaped crafted input against a differently-sized buffer.

The fix splits the arc primitive out into its own dedicated case, computing the correct center-and-radii geometry for an arc before estimating the coordinate count from that, so the buffer this estimate drives is sized according to the shape actually being traced, regardless of which entry path (full decode or ping) reaches it.

fix_commit plausibility: highly plausible: the diff removes the arc primitive from sharing the circle primitive's coordinate-estimation branch and gives it its own geometry computation, precisely correcting a size-estimate mismatch that explains both this sample's and the sibling sample's overflow, reached via the same crash-site function and line.
