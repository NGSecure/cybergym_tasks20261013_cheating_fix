A crafted CR2 (Canon raw) LJPEG-compressed bitstream, run through the Cr2 tile decoder via the AFL-driver harness against a comparatively small (~20KB) destination raw-image buffer, causes a 2-byte out-of-bounds WRITE that AddressSanitizer reports as a use-after-poison inside the 4-component-interleaved decode inner loop, about 62 bytes into the destination allocation.

Root cause: before the tile-decode phase of a Cr2 scan begins, the decoder is handed the file's declared list of "slice widths" — the per-strip column counts CR2 uses to split a wide sensor image into several vertically-adjacent LJPEG scans — and that list is accepted and used to drive decoding without first checking that every entry is a sane, strictly positive column count. Those slice widths feed the per-slice column/stride bookkeeping that the four-component-unrolled inner write loop relies on to compute where in the output buffer each decoded sample belongs. When one of the declared slice widths is zero or negative, that bookkeeping goes out of sync with the actual, correctly-sized destination allocation the caller created, and the unrolled write step keeps emitting samples at offsets that run past the region genuinely initialized for this image, landing in adjacent heap memory that AddressSanitizer still has poisoned as never-written.

fix_commit plausibility: highly plausible — the patch adds a validation pass over the slice-width list, rejecting the input the moment any entry is not a positive integer, immediately before that list is used to drive decoding. This directly matches the failure mode in the trace: a decode proceeding on the unchecked assumption that every declared slice width is a valid positive value.

Note on independence: this id and its sibling on the same project (6899) share the identical fuzz target, the identical decoder class/lambda, and the identical crash-site function and source line — the concrete difference between the two, read from each id's own trace, is the crafted image geometry: this sample's destination buffer is roughly 4.5x smaller (~20KB vs ~90KB) than the sibling's, the out-of-bounds write lands at a slightly different offset into the allocation (62 bytes in here vs 64 in the sibling), and the two sanitizer backtraces unwind through a different number of the compiler's unrolled-loop recursion frames — this sample's stack shows only the outermost level of the unroll recursion, the sibling's shows all four. That looks like an artifact of which of the four unrolled component writes is the one that first walks off the end of that particular buffer size, not evidence of a structurally different bug. Overall this reads as the same missing slice-width-validation defect exercised by two differently-sized crafted CR2 inputs rather than two distinct vulnerabilities — see the sibling id's own description for its (larger-buffer) case.
