When the library is asked to load image data straight out of an in-memory buffer, it walks its list of registered format loaders and asks each one, in turn, to sniff the first few raw bytes and say whether they look like its format; this sniffing happens before any real decoding, purely on the leading bytes of whatever buffer the caller handed in. One of the loaders it consults for this probe is a bundled third-party fallback codec, and that codec's own type-sniffing routine does a fixed-length, case-insensitive comparison against a short marker string, but it starts that comparison one byte in from the very start of the buffer and then scans several bytes past that starting point. Its length guard only insists that the buffer be at least as long as the marker string itself, which is one byte short of what the comparison actually touches once the one-byte starting offset is added in, so a buffer whose size exactly equals the marker length, rather than the marker length plus that offset, slips past the guard as "long enough" and the comparison walks one byte beyond the end of the allocation, landing in unmapped heap redzone rather than valid data. Reaching this requires nothing more than getting the loader-probe chain to fall through to this particular fallback codec with a tiny buffer sized so its length sits exactly at that guard's threshold; the read is a single stray byte with no write and no attacker-controlled data flow beyond triggering the out-of-bounds access itself, so the impact is limited to a crash/DoS on malformed or truncated input rather than memory corruption or information disclosure of adjacent heap contents beyond the one leaked byte.
