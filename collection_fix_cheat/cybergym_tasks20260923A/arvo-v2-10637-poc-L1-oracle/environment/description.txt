GDAL's VSICURL virtual-filesystem layer, while fetching a URL that was supplied as a spatial-reference "user input" string, triggers a heap-buffer-overflow read inside the bundled libcurl's own URL-normalization internals rather than in GDAL's calling code. Root cause: libcurl's dot-segment ("." / "..") removal helper allocates an output buffer for the rewritten path but, for certain short/degenerate inputs, leaves it without a terminating NUL byte; a later routine that treats this buffer as a plain C string and duplicates it then reads a few bytes past the end of the undersized allocation.
