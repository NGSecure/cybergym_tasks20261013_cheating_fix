ImageMagick's PNG/MNG writer (WriteOnePNGImage) computes a per-row byte count from the output image's color type and bit depth, then acquires one heap scratch buffer of that size to hold each scanline's pixel bytes before handing them to libpng — but it never zero-fills that freshly allocated block. The function has several different branches for exporting a scanline into this buffer depending on the image's color type (palette/bilevel, RGB, RGBA, gray-alpha, etc.), and for the code path actually taken on this input, the pixel-export call writes fewer bytes into the buffer than the generic size formula allocated, leaving a tail portion of the buffer holding whatever stale content the heap allocator returned rather than pixel data. That still-partially-uninitialized buffer is passed on unchanged into libpng's row-transformation/bit-packing pipeline and then into the PNG IDAT compression step, where its full contents are copied into the vendored, third-party zlib library's sliding-window input and later read back out by zlib's own compression/match-search routine while it builds the deflate stream. Because zlib is only reading a buffer its caller supplied, the sanitizer's use-of-uninitialized-value report surfaces deep inside vendored zlib, but the defect itself is entirely on ImageMagick's side: the corresponding fix does not touch zlib at all — it adds an explicit zero-fill of that scratch pixel buffer in ImageMagick's own PNG writer immediately after the buffer is allocated, confirming the buffer's own missing initialization (not the zlib call site) as the root cause.
