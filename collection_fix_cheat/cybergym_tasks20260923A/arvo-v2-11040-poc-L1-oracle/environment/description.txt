Decoding an indexed (palette-based) GIF image through Skia's sampled/scaled Android-codec decode path can trigger a heap-buffer-overflow write of 4 bytes just past the end of the destination pixel buffer. The affected routine converts decoded palette-index bytes into 32-bit RGBA output pixels row by row, writing into a destination buffer at a starting byte offset that is derived from the requested horizontal sample rate together with the row width. When decoding proceeds through the sampled/subsampled path rather than a full-resolution decode, the calculation used to derive that starting offset does not correctly account for how subsampling shrinks the number of output pixels relative to the buffer's nominal row width: for certain width/sample-rate combinations the computed offset ends up coinciding with (or exceeding) the true end of the row, leaving no space left in the buffer for the pixel write that immediately follows. Because the destination buffer is sized only for the sampled/scaled output dimensions, the resulting write lands outside that allocation and corrupts adjacent heap memory. The condition is reachable purely by supplying a small, structurally valid indexed GIF whose dimensions and requested sampling rate provoke this offset-computation error through Skia's ordinary public image-decoding API, with no need for malformed byte-level codec state.
