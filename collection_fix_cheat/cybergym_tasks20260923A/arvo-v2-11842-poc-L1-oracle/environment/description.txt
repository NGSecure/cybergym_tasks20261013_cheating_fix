Deserializing a path embedded in a serialized picture (as happens when an image filter tree is reconstructed from raw bytes) can trigger a heap-buffer-overflow read while the library decides whether the resulting path is convex. Root cause: a path object carries an internal bookkeeping value recording where its most recent "move to" command started, and later convexity analysis uses that value as the upper bound on how many of the path's stored points to scan; but the value comes straight from the untrusted serialized stream during deserialization and is only checked to be positive, never checked against how many points the path actually ended up holding after decoding. When the encoded value is larger than the real point count, the convexity scan trusts it anyway and walks a pointer through the point array up to that inflated bound, so the final iteration computes a vector between two supposed path points using memory that lies just past the end of the allocated point buffer.
