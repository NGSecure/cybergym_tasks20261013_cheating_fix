c-blosc2 frame-decompression fuzz target (ASan build): a wild-address read occurs while restoring a single block during chunk decompression, preceded by an ASan warning that an intermediate allocation request for an implausibly large byte count failed. Root cause: the per-block decoder has a special encoding for blocks whose compressed size is signalled as negative -- it reads one extra control byte and branches on its low bit to decide how to materialize the block's output. The vulnerable code only implements the branch taken when that low bit is set; when a crafted stream clears that bit instead, no branch executes at all -- the block's output region is left unpopulated and no error is reported -- yet the byte-count bookkeeping for input consumed and output produced still advances as though a full, valid block had just been written. That corrupted state feeds forward into the chunk's byte-restoration pipeline, which for this crafted input is configured to run the bit-level transpose (bitshuffle) filter: this filter's SIMD transpose routine derives its row/stride geometry only from the (still nominally valid) type size and block size and then walks the block buffer in fixed strided slices under the assumption that the whole region was legitimately produced by the prior decode step. Because that region was never actually written -- its size was faked while its allocation/content lineage is bogus -- the strided read walks off into memory the buffer doesn't actually back, landing on an unmapped/wild address.
