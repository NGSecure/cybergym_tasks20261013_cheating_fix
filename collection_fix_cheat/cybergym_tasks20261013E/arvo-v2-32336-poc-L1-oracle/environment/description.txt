c-blosc2's decompress-frame fuzz target retrieves a single item out of a chunk whose block was compressed with the zstd secondary codec. AddressSanitizer reports a heap-buffer-overflow write of a couple of bytes, occurring inside the codec's own routine for finishing a copy of the tail of a matched byte run, into a small per-block scratch buffer that the item-retrieval path allocates just before invoking the codec. Root cause: the size of that scratch buffer is derived directly from a per-block "block size" field carried in the chunk's own header, and the header parser only checks that this field is positive and does not exceed the chunk's own (equally attacker-controlled) total uncompressed size -- it never enforces any absolute ceiling. A crafted header can pick a legitimately small declared block-size (so the scratch buffer really is undersized) while still embedding a compressed stream whose actual decoded content -- once the codec trusts the caller's declared capacity rather than re-checking it -- runs a couple of bytes past what that undersized buffer can hold. The fix rejects any per-block size above a fixed, sane upper bound as soon as the header is parsed, before any scratch buffer is sized or any codec is invoked.
