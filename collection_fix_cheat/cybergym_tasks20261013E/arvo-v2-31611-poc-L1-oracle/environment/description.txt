c-blosc2's frame-chunk decompressor (decompress_frame_fuzzer target, ASan build): a segmentation fault occurs on a wild-address 4-byte read while setting up per-chunk decompression state, before any actual block data is touched. Root cause: this setup step derives a block count from the header's logical (decompressed) size and a separately-stored block size, then uses that count to size and bounds-check a lookup-table region placed right after the header, and -- when the header's "chunk carries an attached external dictionary" flag is set -- reads a small dictionary-size field located immediately past that lookup-table region. This derivation has no special case for the compact "special value" placeholder chunk representation (all-zero / all-NaN / one-repeated-value runs) that other parts of the library recognize: a chunk flagged as such a placeholder is still run through the same block-count/lookup-table math as an ordinary chunk, even though a genuine placeholder chunk has no real per-block structure or lookup table at all. By combining that placeholder flag with a very large logical size and a tiny block size, the derived block count -- and the byte offset computed from multiplying it by the table's element size -- overflows far past any range the bounds check was designed to catch. When the crafted header also sets the external-dictionary flag, the dictionary-size field is then read from that wildly displaced offset, dereferencing an address nowhere near the real chunk buffer and crashing with SIGSEGV rather than landing in a well-defined heap redzone.
