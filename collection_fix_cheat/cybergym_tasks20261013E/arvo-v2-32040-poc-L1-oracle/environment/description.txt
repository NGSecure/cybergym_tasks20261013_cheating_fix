c-blosc2's decompress-frame fuzz target retrieves a single item out of a chunk whose block uses the bit-level transpose ("bitshuffle") filter. AddressSanitizer reports a heap-buffer-overflow write of just a couple of bytes past the end of an unusually large (over a gigabyte) scratch allocation used to hold the filter's output -- the allocation itself is sized consistently with an inflated declared block size, so this is not a simple "buffer too small for its purpose" bug. Root cause: the same per-block "block size" field from the chunk header, which the header parser only checks against the chunk's own (equally attacker-controlled) total uncompressed size rather than against any absolute ceiling, both drives that oversized allocation and feeds, through internal fixed-width size arithmetic, the element/lane counts the transpose routine's inner loop uses to walk the buffer. Once the field is allowed to take on values far beyond what the filter's fixed group-width (its loop processes elements in small, fixed-size groups) was ever exercised against, the loop's bookkeeping for the last partial group slightly overshoots even this large buffer. The fix rejects any per-block size above a fixed, sane upper bound as soon as the header is parsed, keeping the filter's internal counts within the range its loop was designed for.
