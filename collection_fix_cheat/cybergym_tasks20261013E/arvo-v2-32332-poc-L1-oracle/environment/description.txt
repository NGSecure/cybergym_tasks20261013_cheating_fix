PHP's bundled oniguruma regex engine, reached through the mbstring extension's case-insensitive POSIX-style multi-byte regex matching entry point (php-fuzz-mbstring target, MemorySanitizer build): MemorySanitizer flags a read of an uninitialized byte while the engine's forward-search fast-path is stepping a cursor across the subject string, using a per-character UTF-8 encoding-length lookup table indexed by the byte the cursor currently points at. The interesting part is the origin trace MSan attaches to that uninitialized byte -- it does not lead back to how the subject string was received or copied. It leads back to a realloc() performed inside the regex compiler's internal operand/instruction-array growth routine, invoked while the *pattern* (not the subject text) is being compiled: that array is repeatedly doubled in size as opcodes are emitted for the pattern being parsed. The freshly grown tail of that reallocated heap block is never explicitly written before a later, unrelated code path -- the search-time per-character length lookup -- reads a byte at that same heap location as though it were already-valid data. So the shape of the bug is: a compile-time internal buffer-growth step leaves trailing heap memory content undefined, and a later match/search-time helper implicitly trusts that stale, never-initialized memory as if it were meaningful subject-string data. This is purely an oniguruma pattern-compilation/matching-engine issue; it has no connection to PHP's session-handling subsystem.
