c-blosc2's frame-chunk decompressor (decompress_frame_fuzzer target, ASan build): a heap-buffer-overflow 4-byte read occurs while walking a chunk's per-block compressed-stream table, reading 111 bytes past the end of a 186-byte allocation. Root cause: the library has a compact "special value" chunk representation (a placeholder for an all-zero, all-NaN, or one-repeated-value run) whose physical storage is just the header plus, at most, one stored item -- none of the normal per-block/per-stream layout is actually present. Whether an incoming chunk is decoded through this placeholder path is decided from one flag bit; separately, the general block-decoding routine decides whether to treat a chunk as a flat literal copy (skipping the per-block table entirely) using a different, older flag bit. Nothing keeps these two decisions in agreement: a chunk can have the newer "this is a placeholder" bit set while the older "treat as literal copy" bit is left clear. When that happens, the general block-decoding routine falls through into its normal path meant for real block-compressed data: it derives a starting offset from a lookup table that a genuine placeholder chunk never contains, then loops once per compressed sub-stream reading a 4-byte "length of this sub-stream" prefix and advancing through the buffer accordingly. Because the actual allocation backing a placeholder chunk is only header-sized, those repeated length-prefix reads run straight off the end of the buffer.
