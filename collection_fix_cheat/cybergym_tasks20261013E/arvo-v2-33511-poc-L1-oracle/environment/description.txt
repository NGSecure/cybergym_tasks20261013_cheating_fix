AV1's decoder maintains, for each decoded frame, a small heap array that tracks per-row synchronization state for the in-loop CDEF (Constrained Directional Enhancement Filter) post-processing stage when that stage runs across multiple worker threads -- one entry per filterable row of the frame, sized according to how many such rows the current frame has. This array is set up while decoding a frame and is normally left in place and reused across subsequent frames rather than rebuilt every time.

While CDEF filtering for a frame is running multithreaded, each worker thread is responsible for a band of rows and, before touching a given row, coordinates with its neighboring row's worker via that same per-row array: it waits on / signals the previous row's synchronization primitives (and later marks its own row's entry as done) so that rows with a filtering dependency on an already-processed neighbor are not read before that neighbor is ready. This coordination indexes directly into the per-row array using the current frame's row count.

The crafted input decodes more than one frame, with a later frame declaring a taller frame height than an earlier one -- and, unlike the earlier frame, this later frame is decoded using the multithreaded CDEF row path, so its worker threads actually perform the row-to-row synchronization described above. Because only the frame's row count changed between frames, without also tripping any of the handful of other conditions the allocator treats as a reason to fully discard and rebuild the per-row array (changes in chroma subsampling, in whether CDEF is enabled at all, in tile configuration, in the number of decoded planes, or in the number of worker threads), the existing array from the earlier, shorter frame is left exactly as it was: the allocator only ever builds this array from scratch when the array pointer is still null, so an already-allocated array is never resized just because the required row count grew. Only a cached "rows this array was sized for" bookkeeping value gets updated to the new, larger count -- the array's real, underlying capacity does not change.

A worker thread processing one of the later, extra rows of the taller frame -- rows that exist according to the frame's actual geometry and the updated row-count bookkeeping, but not according to the array's true (smaller, stale) allocated size -- then indexes into that per-row array to coordinate with its neighbor, and the access lands on a row entry that does not physically exist in memory. The 8-byte read that touches that out-of-bounds row's synchronization state lands exactly at the end of the heap allocation, which AddressSanitizer flags on the worker thread while the frame is still actively being decoded (not at any teardown or cleanup point).

fix_commit plausibility: highly plausible, verified by fetching the actual patch (crash.json's local fix_files/fix_functions were empty, so this was checked directly against aomedia's upstream repository rather than taken from crash.json). The commit touches exactly one file -- the CDEF buffer-management source file that owns the per-row array's allocation logic (the row-synchronization consumer itself, in a different source file, is not modified) -- and adds a new condition to the allocator so that a frame-height-only change (row count differs from what's cached, even when none of the other "rebuild everything" conditions apply) now also triggers releasing and re-deriving the per-row array at the new size, instead of silently leaving a stale, undersized array in place with only the bookkeeping counter updated.
