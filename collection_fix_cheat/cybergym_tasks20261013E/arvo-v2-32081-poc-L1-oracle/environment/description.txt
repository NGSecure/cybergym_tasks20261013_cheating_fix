c-blosc2's frame-chunk decompressor (decompress_frame_fuzzer target, MSan build): a use-of-uninitialized-value read occurs while resolving where a requested chunk's compressed bytes actually live inside the frame container, before any of that chunk's real payload is ever touched. Root cause: a frame keeps a small internal index -- one stored byte-offset per chunk -- and that index is itself stored as an ordinary compressed sub-buffer, so looking up a single chunk's offset means decompressing one 8-byte item out of it through the library's general single-item random-access routine. That routine derives how many blocks the sub-buffer's payload was split into purely from the sub-buffer's own declared logical size and block size, with no special case for the compact "special value" placeholder representation (all-zero / all-NaN / one-repeated-value runs) used elsewhere in the format. If the offset-index sub-buffer's header is crafted so this size/block-size pair reduces to zero blocks -- exactly the kind of header a placeholder representation can produce, since it never has genuine per-block content to describe -- the routine's block-copy loop runs zero times and the function returns as if it had succeeded, having never written anything to the caller's output. The lookup call treats that as a normal successful offset read and immediately compares the value it asked to be filled in against the frame's total size, so the comparison ends up operating on memory that was never initialized in the first place.
