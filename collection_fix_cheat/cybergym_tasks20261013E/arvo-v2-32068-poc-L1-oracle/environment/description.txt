c-blosc2's item-decompression path crashes with a wild out-of-bounds read while unpacking a Zstd-compressed block, because it writes decoded bytes into a per-thread scratch buffer whose earlier allocation was never checked for failure. When an item is extracted through the library's random-access getitem path and the target chunk's filter pipeline is non-empty, decompression is directed into a scratch buffer that lives inside a per-thread working context created on demand for the call. That scratch buffer's byte size is derived directly from the block size and per-element size recorded in the chunk's own header, with no upper bound applied, and is handed to the allocator without the caller ever inspecting whether the allocation actually succeeded; several further working-buffer pointers inside the same context are then computed by adding fixed offsets on top of that (possibly null) result. When a crafted header makes the requested size large enough that the allocator returns null, the scratch pointer and every pointer derived from it are simply null-plus-offset values, yet execution proceeds to hand one of these bogus pointers to the codec as the destination for the current block. The Zstd decoder treats that destination as an ordinary, writable output window: while resolving a back-reference during decoding it computes a source address by subtracting an offset from the current (garbage) write position, and that computed source address lands on a completely unmapped page, so the very first byte-copy of the match triggers a wild, out-of-bounds read that the sanitizer reports as a crash deep inside its own memory-access instrumentation rather than in application code.
