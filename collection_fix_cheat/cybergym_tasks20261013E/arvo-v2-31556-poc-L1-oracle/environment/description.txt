c-blosc2 (ASan build, decompress_frame_fuzzer target): while decompressing a chunk located inside an in-memory frame, the frame layer resolves the requested chunk index to a compressed-chunk pointer and declared compressed length by reading the matching entry out of the frame's per-chunk offsets index, then hands that (pointer, length) pair to the block decompressor, which walks the chunk's block table and expands the shuffled bytes for each block in turn, one after another. Root cause: the boundary check applied when the offsets index computes a chunk's declared compressed length only bounds that length value against the frame's total size, but never accounts for the position at which the chunk itself begins inside the frame -- so a chunk that starts far enough into the frame can have a declared length that looks individually in-range, yet once its start position is added on top, the resulting span extends well past the frame's real backing allocation. The block decompressor has no way to detect this: it processes the first several blocks normally, since their bytes are still backed by genuinely valid memory, and only runs off the end of the true allocation partway through the block-table walk -- at which point a routine little-endian 4-byte field read performed deep inside that per-block loop lands outside the buffer.
