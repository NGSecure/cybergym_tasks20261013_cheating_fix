SerenityOS's LibMarkdown table parser, while scanning the heading-delimiter row of a Markdown table (the line of dashes/colons under the header that specifies per-column alignment, e.g. `:---`, `---:`, `:--:`), extracts each delimiter cell as a text span and checks it against a single-character alignment marker using a generic span-vs-C-string equality routine shared across the codebase. When a delimiter cell contains characters other than the expected alignment markers, the parser keeps scanning the cell (so it can later emit a diagnostic about an invalid character in the delimiter), which can make the extracted span considerably longer than the one-character marker literal it is compared against. Root cause: the equality routine's comparison loop is driven purely by the length of the left-hand span, not by the length of the right-hand literal -- it walks forward one byte at a time for exactly as many iterations as the span is long, without first checking whether it has already advanced past the literal's terminating null byte. Once the span is longer than the marker literal, later loop iterations dereference memory immediately past the literal's storage, which in this build happens to be read-only global data belonging to another, unrelated string constant laid out directly after it -- yielding a one-byte out-of-bounds read from a global buffer (not from heap or stack memory). The crash therefore requires a table heading-delimiter cell whose non-alignment-character content is long enough to overrun the short literal being compared against, not merely an "invalid" delimiter cell of any length.
