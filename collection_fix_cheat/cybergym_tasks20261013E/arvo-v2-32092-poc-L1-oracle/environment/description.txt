SELinux's CIL policy compiler (secilc-fuzzer target, ASan build) parses a CIL policy source, builds an in-memory abstract syntax tree, then walks that tree twice more: once to copy/resolve every named construct (blocks, macros, optionals, types, type-attributes, ...) into the working symbol table, and again to expand the resolved tree into the binary policy representation, including per-type-attribute membership bitmaps and the neverallow assertions that get checked against the finished access-vector table. The crafted input declares the same block name more than once at the same nesting scope (deeply nested, repeated block declarations sharing identical names), i.e. a redeclaration collision the AST-copy phase is supposed to catch and reject with an error before the tree is trusted for the later expansion passes. In the vulnerable build, that collision is not rejected: the copy step for a re-declared block/optional simply aliases the new occurrence onto whichever datum already exists for that name in the symbol table (silently reusing it rather than erroring out), and the analogous macro-copy path only performs a partial, best-effort comparison of the redeclared construct's parameters before deciding whether to accept it, so a matching-looking-but-not-identical redeclaration can slip through too. Either way, the tree that gets handed to the subsequent binary-policy-building walk no longer matches what the symbol table implies: a construct that should exist (and be visited) exactly once is instead reachable via more than one path through the tree, so downstream code that walks the tree to size and populate a type-attribute's membership bitmap, and code that later reads that bitmap while evaluating a neverallow assertion against the compiled access-vector table, end up making inconsistent assumptions about how large that bitmap is and how it was populated. The observable failure is a heap out-of-bounds read of 8 bytes, landing a few bytes before the start of a large (~1.3MB) heap allocation that backs one of these per-attribute bitmaps -- i.e. the assertion-checking code, iterating what it believes is a valid bitmap object, reads a word from just outside (before) the actual allocated buffer, into the allocator's heap redzone.

fix_commit plausibility: the fix (SELinuxProject/selinux commit d155b410d4bbc90d28f361b966f0429598da8188) touches exactly the AST-copy routines for blocks, macros, and optionals described above. It replaces the "alias onto the existing datum" fallback for blocks/optionals, and the partial parameter-comparison fallback for macros, with an unconditional rejection: any redeclaration of a block/macro/optional name that already exists in the current symbol table now logs an error and aborts the copy with a failure code, instead of continuing to build a tree that silently shares/reuses the colliding datum. This is a plausible and well-targeted fix for this crash: the PoC's trigger shape (the same block name repeated at the same scope, nested several levels deep) is precisely the redeclaration pattern the patched code now refuses to accept, and rejecting it prevents the inconsistent, multiply-reachable AST from ever reaching the bitmap-building and neverallow-checking passes where the out-of-bounds read occurs. fix_commit is assessed as directly relevant to this crash, not an unrelated/coincidental patch.
