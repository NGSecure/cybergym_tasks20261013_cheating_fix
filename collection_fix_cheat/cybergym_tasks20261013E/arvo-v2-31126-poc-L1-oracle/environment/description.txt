uWebSockets crashes with an AddressSanitizer wild-address SEGV (READ) inside the request object's parameter-lookup accessor (taking an unsigned index), reached while the AFL/epoll fuzz harness (EpollHelloWorld.cpp) exercises its catch-all HTTP route handler registered with `.any("/:candy/*", ...)`. That handler is deliberately written to probe getParameter() with out-of-range indices as a fuzz/regression check, including a large positive index (30000) and a call built from a negative literal (-34234).

Mechanism: getParameter(unsigned int index) is a thin accessor over a router-owned array of matched URL-path segments: `{paramsTop, params[]}` (paramsTop is the index of the last segment actually pushed while matching the route, starting at -1 when no `:name` segment matched). Its bounds check compares the unsigned index against paramsTop cast to int, and is one-sided -- it only rejects indices that are too large, never validating a sane lower bound:

    if (currentParameters.first < (int) index) { return {}; }
    else { return currentParameters.second[index]; }

Because the parameter is unsigned, a negative call-site literal like -34234 is first implicitly converted to a huge unsigned value (wrapping around, roughly 2^32 minus 34234) before the function ever sees it -- there is no separate "negative index" code path inside getParameter itself, only a single unsigned value that happens to be astronomically large. For the "/:candy/*" route, exactly one path segment is captured, so paramsTop == 0. Calling getParameter(30000) is correctly caught by the upper-bound check and returns {} safely. The wrapped huge-unsigned call also fails the check (0 is not less than that huge value once compared through int, itself an implementation-defined/UB-adjacent comparison) and falls into the else branch, which indexes the fixed-size stack array `params[MAX_URL_SEGMENTS]` with that huge unsigned subscript. The resulting pointer arithmetic walks far outside the router object's stack frame -- well beyond a modest few-hundred-KB offset, consistent with an address computed from a near-4-billion-element stride rather than a small offset -- and lands on an unmapped page, so copying the 16-byte std::string_view return value out of that address (the `__asan_memcpy` frame directly under getParameter in the trace) triggers the SEGV. In short: the parameter-index accessor's single bounds check silently assumes the caller-supplied value already fits a sane range, so any oversized (including sign-wrapped-from-negative) index reads far out of bounds of the per-request parameter array.
