c-blosc2's frame-decompression fuzz target (ASan build): feeding it a crafted multi-chunk frame that uses a per-chunk trained dictionary produces a heap-use-after-free read, not during decoding itself but later, when the fully-decoded super-chunk object is torn down and its decompression context is released -- the crash happens inside the third-party Zstd library's own dictionary-object destructor. Root cause: the reusable decompression context that is shared across every chunk of a super-chunk caches one live Zstd dictionary object as a field on that context; the reload path that runs at the top of each dictionary-bearing chunk's header parsing frees whatever dictionary object is currently cached there up front (on the assumption it belonged to a previous, unrelated chunk), and only overwrites that cached field with a freshly built dictionary object once it has validated the new chunk's declared dictionary size against the number of bytes actually remaining in the chunk. Several of those size checks can fail and return an error immediately, and none of the failing paths clears or restores the cached field first, so the context is left holding a pointer to memory that was just released. Nothing dereferences that stale pointer again during decoding -- the failed chunk is simply reported as an error and skipped -- so the corrupted context survives all the way to final cleanup, at which point releasing the context calls into the same dictionary-object destructor a second time on the identical pointer, i.e. a double free that AddressSanitizer reports as a read of already-freed heap memory. Getting the decoder to walk into that dictionary-reload path at all on a chunk that was never meant to carry a dictionary requires it to first be pointed at the wrong location and length for that chunk's compressed bytes -- which is exactly what the accompanying fix addresses: the code that resolves a chunk index to a byte offset and length inside the frame trusted the frame's declared chunk count without ever checking it against how many offset entries the frame's own offset table actually holds, so a frame whose offset table encodes a different count than the frame header claims could make offset/length resolution for a given chunk index land on bytes that do not describe a real chunk boundary; those bytes then get parsed as if they were a legitimate chunk header, including whatever byte happens to fall on the dictionary-flag position, sending decoding down the per-chunk dictionary-reload path for a index that has nothing to do with a dictionary. The patch adds exactly that missing cross-check on the offset table's entry count before any chunk offset/length derived from it is trusted.
