A crafted regex pattern that gives the compiled matcher a very large maximum-possible-match-length distance value triggers an out-of-bounds read / SIGSEGV (UBSan) while the engine computes the lower bound of its next search window over a UTF-8-encoded haystack. Root cause: the code deciding whether the current match start is already close enough to the beginning of the string (so the lower bound can just be clamped to the string start, no further adjustment needed) compares the current byte offset against that maximum-distance value only after implicitly truncating the distance to a narrower signed integer for the comparison. For a distance value large enough to overflow that narrower type, the truncated value used to pick the branch no longer agrees with the full-width value used moments later, when the taken branch actually subtracts the (untruncated) distance from the current position to compute a fallback lower bound. That mismatch lets the subtraction produce a pointer address far outside the buffer -- the reported crash address carries the tell-tale sign-extended high bytes of a truncated-then-subtracted 32-bit quantity -- which is then handed to a helper that walks backward one byte at a time looking for a valid multi-byte lead byte. It is that backward walk over unmapped memory that actually dereferences invalid memory and segfaults; the multi-byte lead-byte classification logic itself is not at fault. The defect is purely in the search-window lower-bound bookkeeping when the pattern's maximum match distance is large enough to overflow the comparison's narrower integer type.
