One-sentence summary: wasm3's OSS-Fuzz libFuzzer target (UBSan build) feeds an arbitrary byte blob straight into the WebAssembly module parser/loader; loading a minimal module whose global-variable-declarations section carries a long, unbalanced chain of constant-push opcodes in one global's initializer expression silently overflows the interpreter's own execution-stack buffer during load, corrupting adjacent heap memory -- the corruption only actually surfaces later, as a SIGSEGV read fault inside the C library's own free() when runtime teardown dereferences a pointer-sized field that the overflow had overwritten with garbage.

Crash mechanism:
- Each global's declaration includes a small constant-initializer expression (a short sequence of const-push opcodes) that the loader must evaluate once, at load time, to produce the global's initial value. wasm3 evaluates this expression by routing it through the same general-purpose expression compiler used for ordinary function bodies, and then immediately executing the compiled instructions against the runtime's real, already-allocated execution-stack buffer (rather than a throwaway scratch buffer) to read back the result.
- Ordinarily, compiling code inside a real function body tracks how many stack slots the code being compiled will need and checks that figure against the runtime's actual stack capacity before letting anything execute. That tracking step was, at the time of this crash, wired up only for the "compiling inside a real function" case; compiling a global's constant-initializer expression takes the identical code path but without ever being inside a function, so the slot-count bookkeeping this path depends on was silently never updated, and consequently the pre-execution capacity check had nothing meaningful to compare against.
- A global initializer built from many chained constant-push opcodes with no corresponding pops (well beyond what a normal, small initializer would ever need) drives this blind spot: each push writes another value onto the real runtime stack buffer with no capacity check stopping it, so the buffer is filled and then overrun, writing past its end into whatever heap memory happens to sit adjacent to it.
- That adjacent memory is not necessarily related to the global-initializer machinery at all -- it is simply whatever the allocator placed next to the runtime's stack buffer. In this reproduction, the overflow lands on and corrupts a pointer-sized bookkeeping field belonging to the module object itself. The corruption is silent at the moment it happens: nothing in the load path notices, and loading is treated as fully successful.
- The fuzz target's standard sequence for a "successfully loaded" module is to attempt to look up an exported function and then unconditionally tear the whole runtime down before returning. Runtime teardown walks its list of live modules and, for each one, individually frees several of the module's own bookkeeping fields. One of those fields is exactly the pointer-sized value the earlier stack overflow overwrote; by the time teardown reaches it, its bytes no longer represent a real heap pointer at all (the fault address reported is an implausible, effectively-negative 64-bit value). Handing that garbage value to the C library's deallocator faults immediately, because the very first thing a deallocator does is read the target chunk's own bookkeeping bytes just ahead of the supplied address to figure out how to reclaim it -- which is why the crash is reported inside free() itself, on an ordinary-looking single free() call, even though the real defect (the unbounded stack write) happened much earlier, during module loading, and far away from any code that looks like it manipulates pointers.

Fix verification: the commit recorded in this id's metadata is very likely one step too late in the repository's history to be the actual fix. That recorded commit's own visible changes (a handful of module-parsing/bookkeeping refactors, including closing an unrelated overwrite-without-release gap in export-name handling) do not touch the expression compiler or the global/data-segment initializer-evaluation path described above, and this PoC's payload contains no export section at all, so the one memory-safety-relevant hunk in that diff cannot be what this specific input exercises. Comparing commit timestamps and diff content in the surrounding history points instead to that commit's immediate parent as the real fix: a same-day, slightly earlier commit whose explicit purpose (per its own commit message) is adding stack-overflow detection to the constant-initializer-expression evaluation path -- it adds the missing capacity check comparing the tracked stack-slot count against the runtime's real stack capacity, and extends the slot-count tracking so it also fires when compiling outside of a real function context (exactly the global/data-segment initializer case implicated here). Because the commit recorded in this id's metadata is a direct descendant of that real fix, empirically re-running this id's differential against the recorded commit still correctly shows "no longer crashes" -- it inherits the real fix from its parent -- which is presumably how the recorded commit came to be associated with this id in the first place, even though it is not itself where the fix was introduced.
