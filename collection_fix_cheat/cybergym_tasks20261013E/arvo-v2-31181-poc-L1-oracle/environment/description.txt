LibRaw's libFuzzer raw-image-decoding target (ASan build) hits a 1-byte heap-buffer-overflow READ inside LibRaw's Kodak "C330"-style YCbCr raw-scanline decoder, reached from the library's main unpack() dispatcher once the file's metadata has been identified as that legacy Kodak sub-format. For each output row the decoder fread()s one interleaved luma/chroma scanline into a freshly heap-allocated scratch byte buffer sized raw_width*2 bytes, where raw_width is the full raw-row width parsed from the file's metadata. It then walks the output columns 0..width-1 (width being a second, independently-parsed output-width field) and, for each column, derives three byte offsets from col*2 to pull the luma sample and its two enclosing chroma samples out of that scanline buffer: the exact offset col*2 for luma, and, to reach the Cb/Cr bytes shared by the surrounding 4-byte YCbCr group, the column's byte offset rounded down to the nearest multiple of 4 with bit 0 or bit 1 OR'd back in. Root cause: this rounding-based chroma-offset arithmetic is never bounds-checked against the buffer's actual raw_width*2-byte size, and it overruns the buffer even in the ordinary, uncropped case where width equals raw_width -- whenever raw_width is odd, the last column's rounded-down-then-OR'd Cr offset lands one byte past the two-scanline buffer's last valid byte, which is exactly the 1-byte overread ASan reports; nothing in the decode loop constrains the derived offsets to stay inside the allocated buffer, regardless of raw_width's parity or of any mismatch between raw_width and width.
