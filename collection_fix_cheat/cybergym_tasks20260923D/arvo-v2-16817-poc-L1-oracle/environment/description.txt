During in-loop filtering, the decoder keeps a small per-coding-tree-block bookkeeping array whose size is derived from the picture's coding-tree-block grid and which records boundary/slice-continuity state as processing sweeps across a frame block by block. While applying the sample-adaptive-offset stage and shifting this bookkeeping state forward to the next coding-tree-block position, the code computes the array slot for the block that has just finished and stores a single byte into it without first confirming the computed slot is still within the allocated array. For a stream whose picture dimensions, or slice/tile boundary layout, push this shift operation to the picture's final coding-tree-block row or column, the computed slot lands exactly one element past the array's last valid entry, so the one-byte store falls into the heap redzone immediately following the buffer rather than inside it. This path is reached for any slice type, not one specific to intra-coded pictures, and the errant write is always a forward, past-the-end overrun rather than a write before the buffer's start; the bad index is effectively an off-by-one at the tail of the array rather than a wildly out-of-range value, meaning the underlying flaw is a missing upper-bound check on the shift index rather than a size or sign computation gone badly wrong.
