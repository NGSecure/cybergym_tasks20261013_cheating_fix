This crash is reached inside the same Commissioner "get"-request handling logic in the Thread network-data leader, but the overflow occurs one step earlier than a companion, otherwise-independent bug in this code: rather than surfacing only when the collected data is later read back out, this manifestation happens while the handler is still assembling that data. The handler extracts a declared value-length from an attacker-controlled header field and immediately uses that raw, unvalidated length as the byte count for a direct copy of message-body bytes into a small fixed-capacity array living on its own stack frame, sized only for the maximum a legitimate Network Data payload should require. Nothing compares the attacker-supplied length against that array's actual capacity before the copy runs, so a request whose header advertises a value-length substantially larger than the array can hold causes the underlying copy routine to keep writing well past the array's end, corrupting adjacent stack memory in a single multi-byte write rather than a one-byte slip. The proof of concept reaches this code by constructing an outbound IPv6 datagram-send path rather than delivering a raw received radio frame, so the overflow triggers immediately during population of the array from network-controlled input, before any response is ever built or any lookup loop runs over the (in this case never even validly filled) array contents — a large, direct write overrun driven by an unchecked length rather than the narrow off-by-one read that occurs on the sibling code path once a barely-too-large length is instead accepted and only later walked.
