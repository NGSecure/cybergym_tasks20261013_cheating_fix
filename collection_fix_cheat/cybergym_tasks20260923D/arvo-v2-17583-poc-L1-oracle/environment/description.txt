While loading a JPEG image, the library reads and interprets the embedded camera-metadata (EXIF) directory, and while stringifying one particular metadata entry it applies a heuristic that first looks up a sibling entry (the one recording the camera's manufacturer name) and compares its raw byte payload against a short fixed literal brand string using a fixed-length byte-wise comparison; if that matches, it goes on to compare a second sibling entry (the camera model name) against several longer fixed literal model strings the same way. Both comparisons assume the referenced entry's data buffer is at least as long as the literal string being compared against, but the code never checks the entry's own recorded/allocated byte length against that assumed minimum before walking through it. Each metadata entry's backing buffer is allocated exactly as large as the entry itself declares, so a hand-crafted directory can declare a manufacturer or model entry whose true length is degenerate — far shorter than the literal marker being compared, down to a single byte — while still passing through the same code path that assumes a full-length buffer. The fixed-length comparison then keeps reading sequentially past the true end of that undersized heap allocation for the couple of bytes it's still missing, producing an out-of-bounds read a byte or two beyond the buffer's boundary. Because this happens purely during metadata/header interpretation, before any pixel decoding begins, the overflow read fires very early in file parsing and only in the read direction, never touching a write; a sound fix has to make the length check unconditional and apply it identically at every place this brand/model literal-comparison heuristic is used, not only guard one of the two comparisons, since a partial fix leaves the sibling comparison equally reachable with the same class of undersized entry.
