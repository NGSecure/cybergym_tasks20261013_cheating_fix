During HEVC decoding this decoder can fan slice and picture processing out across multiple worker threads whenever it is configured to use more than one processing core. To do this, the thread that is driving a single decode call builds a short-lived decode-command object on its own stack and then wakes a background worker thread, handing it a pointer into that object rather than a self-contained, independently-owned copy of the data; the worker is expected to keep consuming that pointer asynchronously while the calling thread moves on. Nothing actually guarantees the worker finishes reading through that pointer before the calling function returns and its stack frame (and therefore the command object living inside it) is torn down and reused, so on an unlucky scheduling interleaving the worker thread ends up performing an eight-byte read through a pointer whose target has already gone out of scope, pulling stale bytes out of what is now dead stack space that used to hold one of the command object's fields. This is not a bounds or index bug and it does not depend on any particular value inside the bitstream being too large or too small; it is a lifetime race between an asynchronous per-core decode worker and the synchronous call frame that spawned it, where the object being read is legitimate and correctly sized but has simply already ceased to exist by the time the worker gets around to dereferencing it, so the fix has to make the worker's view of that data outlive the parent call rather than changing any size or bounds check.
