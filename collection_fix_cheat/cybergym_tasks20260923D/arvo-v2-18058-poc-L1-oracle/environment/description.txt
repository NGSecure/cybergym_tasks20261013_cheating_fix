A multithreaded HEVC decode worker crashes with a 4-byte out-of-bounds heap read while updating a per-coding-tree-block neighbor-PU index table that is later consumed for boundary-strength and motion-vector bookkeeping. That index table is a small, fixed-capacity scratch buffer carved out of the tail end of one large combined allocation made once when the codec instance is created, and it is meant to hold one row/column entry per minimum prediction-unit position within a single coding tree block, sized generously enough to cover the largest coding-tree-block size the format allows. The row and column extents actually walked when copying entries out of that table for the current block are recomputed on the fly from the coding-tree-block size recorded in the active sequence-parameter-set object, rather than from whatever geometry was in force when the table was originally populated for this frame. The decoder lets a sequence-parameter-set identifier be re-signaled later in the stream with a different coding-tree-block size than it had before, and reuses the same in-memory parameter-set slot in place without first checking whether that slot's previously recorded coding-tree-block size still matches, and without forcing any resize or a stall until frames still relying on the old geometry have finished their asynchronous processing. When that happens, a worker thread still finishing a frame that was parsed and populated under the smaller, original coding-tree-block size can end up computing its neighbor-table row/column bounds from the larger, just-overwritten value instead, so the derived per-block minimum-prediction-unit count grows past what the scratch table was ever written for. The copy loop then keeps advancing its read index using that inflated, unclamped extent, walking straight past the end of the small neighbor-index table and off the tail of the entire backing allocation, landing a few bytes into unmapped heap redzone on a plain load rather than a store. The unsafe quantity is a size derived from CTB dimensions that keeps growing without being checked against the table's real, already-fixed capacity, and the corrupted state that lets it happen is the unguarded in-place reuse of a parameter-set slot's coding-tree-block size across two frames that should have been kept geometrically consistent or forced through a full reallocation before either could proceed.
