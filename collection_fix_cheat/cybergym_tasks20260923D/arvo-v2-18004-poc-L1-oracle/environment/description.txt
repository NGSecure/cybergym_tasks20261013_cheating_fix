In this userland SCTP stack, AddressSanitizer reports a heap-use-after-free read of two bytes while the stack is reporting a peer-address-change event up to the application layer. This happens while handling the "delete address" side of a dynamic-address-reconfiguration exchange: an address that had earlier been added to the association (allocating a per-remote-address bookkeeping structure) is now being removed as part of processing a delete request, and the code tears down that bookkeeping structure -- freeing its backing memory -- as one of the first steps of the removal. Immediately afterward, still within that same removal step, the code needs to notify the upper layer that this peer address has changed status, and does so by reading a field out of the very bookkeeping structure it just freed, rather than having captured that field beforehand or deferring the free until after the notification is built. The read therefore lands squarely inside memory that had already been released a few instructions earlier in the identical code path: the ordering is inverted, freeing the address record before the data it still needed to describe that removal had been extracted from it.
