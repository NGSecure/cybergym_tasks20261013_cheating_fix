This is a heap out-of-bounds read in the HEVC (H.265) software video decoder, triggered while it is parsing the coded slice data of a picture and building the list of spatial merge candidates for an inter-predicted prediction unit during motion-compensation setup. To assemble that candidate list the decoder pulls in the previously stored motion information (motion vector components and reference indices) belonging to a neighboring block, and it does so by computing which neighbor to fetch from the current block's position, partition geometry, and an availability flag rather than treating that neighbor as already validated. On a bitstream that manipulates these geometry/availability inputs into an unusual combination, the computed neighbor location degenerates into a value that no longer corresponds to any real, already-decoded block adjacent to the current one, and the decoder proceeds to read four bytes from the address it derives from that bad neighbor reference. The crash report itself flags this address as "a wild pointer" and scores it as a far-from-bounds access rather than a small one-past-the-end overrun, meaning the faulty computation is not off by a few elements but produces an essentially arbitrary offset into (or entirely outside) the heap arena that holds the per-block motion-information records. The access is a plain read of a single 4-byte field, occurring before any motion-compensation output is written, so the bug is purely in how the neighbor's storage location is derived, not in any subsequent copy or write path.
