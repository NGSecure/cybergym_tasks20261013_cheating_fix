This is a heap-buffer-overflow read discovered while fuzzing Skia's bitmap-drawing entry points, triggered inside a raster pipeline stage that gathers two 16-bit-per-channel floating-point components per pixel out of a pixel buffer, feeding them into a wide SIMD lane so that a fixed number of pixels can be processed together. When the number of pixels remaining in a row is not an exact multiple of the SIMD width, the pipeline falls into a tail-handling branch that must load whatever partial group of trailing pixels is left (one, two, or three, out of a four-wide lane) using narrower loads for smaller counts. For the specific case of a three-pixel tail, the code takes a shortcut and performs a single wide 64-bit vector load meant to fill in the last two channel values, but that load unconditionally pulls in a full extra pixel's worth of data (both of that next pixel's channel values) even though only one further pixel's channels are actually still valid within the allocated buffer; the buffer itself was sized to hold exactly the drawn rectangle's pixels, with nothing beyond it. Because the load reads more data than the tail actually contains, it walks a few bytes past the end of the allocation into unmapped/poisoned shadow memory, which AddressSanitizer flags as an out-of-bounds read rather than a write. The fix replaces that single wide load with two separate, narrower single-element loads for exactly the channels that are known to be valid, so the tail case with one pixel remaining no longer speculatively reads a full pixel's worth (two channels) from data that isn't there.
