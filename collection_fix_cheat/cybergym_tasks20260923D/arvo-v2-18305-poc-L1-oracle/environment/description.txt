The crash surfaces while the TIFF reader is finishing up its pass over a crafted image, well after it has already pulled the mandatory header fields — including the small, fixed-width count of samples that make up each pixel — into a local variable sized to hold exactly that width. Later in the same routine, after the reader has additionally walked the file's embedded color-profile and EXIF-style metadata (fully attacker-controlled content), it redundantly asks the underlying TIFF metadata layer for that very same per-pixel sample count a second time, reusing the identical, already-populated local as the destination. This second, unnecessary query is the one that goes wrong: instead of writing the same narrow value it wrote the first time, the metadata layer ends up performing a wider write through the pointer than the destination was ever allocated to hold, so the extra bytes spill past the end of that stack slot and stomp on adjacent stack memory, which the sanitizer's redzone catches as an out-of-bounds write. The defect is not a data-driven miscalculation of the sample count itself — that value stays small and in-range throughout — and the destination's own size never changes to accommodate anything; the mismatch is purely between the fixed, narrow storage the caller set aside once and a write the callee performs as if a larger quantity were expected the second time around. Because the first, identical-looking read at the top of the function completes safely, only the later, avoidable repeat of the same query triggers the overflow, which is why the crash reproduces reliably yet only appears deep into processing rather than at the point the tag is first read.
